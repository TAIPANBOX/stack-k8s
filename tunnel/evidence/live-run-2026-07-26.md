# The split, applied to a live cluster

Hetzner, five nodes, k3s v1.36.2+k3s1. Applied 2026-07-26 with `./tunnel/up.sh`
after `kubectl delete ns agent-console` took the previous shape down.

Volumes were deliberately NOT migrated. Re-binding three Longhorn PVs across
namespaces is a manual dance `up.sh` does not script and no operator would
perform, so carrying them over would have tested a warm path rather than the
script. The cost was checked before it was paid: the public CT log showed one
Let's Encrypt certificate for `box.it-rat.com` in the preceding seven days, so a
fresh `caddy-data` would issue the second of five allowed. The operator password
was regenerated; an enrolled passkey has to be enrolled again.

That second certificate was then confirmed rather than assumed, and confirming
it needed care (GOTCHAS 54). Its `not_before` reads `11:44:21`, an hour before
the apply, which on its face says Caddy reused something. It did not: Let's
Encrypt backdates `notBefore` for clock skew, and the CT log's own
`entry_timestamp` for that serial is `12:42:52`, which is the minute `up.sh`
ran. Two certificates this week, three left.

## What the apply found

Five things, all one shape: a component or a check that could not tell "this
deployment does not need me" from "I failed". They are GOTCHAS 51, 52 and 53,
plus a scheme printed as `http://` beside port 443, plus a `rollout status` that
passed on a dying container. Fixed in `0ffa935`.

The point worth keeping is that the first apply went red, in `up.sh`, at the one
check written to be unfalsifiable by design: not "did the pods start" but "can
the console complete a TLS handshake to the daemon". The pods had started. Both
rollouts reported success. The tunnel container was already dead.

## What is proven

The console runs in `agent-stack` under enforced PodSecurity `restricted`. The
daemon runs in `agent-tunnel` with NET_ADMIN and a `/dev/net/tun` hostPath. They
speak over TLS 1.3 with a bearer, through a proxy that reads the protocol.

Asked for the daemon's state, the console answers:

```json
{"backend":"uapi","iface":"wg-op","listen_port":31820,
 "server_public_key":"kEiXctbSSI0o/dUSoduXX9BlCj13OCT3ZR6ED0jVsms="}
```

`backend: uapi`, so this is the network transport and not the shell fallback.
The key matches what the daemon printed at startup, and it is the PUBLIC half:
the daemon reports its private key over UAPI, and the proxy substitutes. The
private key never crossed.

A device issued from the console arrives in the daemon. Asked directly, not
through the console:

```
interface: wg-op
  public key: kEiXctbSSI0o/dUSoduXX9BlCj13OCT3ZR6ED0jVsms=
  listening port: 31820
peer: FOIK3xzDySFKJJZIqoqqoMRKt+9gn4kzPmvfv4bbr2s=
  allowed ips: 10.9.0.2/32
```

Six attacks from inside the console pod, on the real path:

| attempt | result |
|---|---|
| no bearer at all | refused |
| a wrong bearer | refused |
| correct bearer + `replace_peers=true` | refused |
| correct bearer + `private_key=...` | refused |
| correct bearer + `listen_port=51821` | refused |
| correct bearer + `fwmark=1` | refused |
| correct bearer + `get=1` | forwarded, `interface_public_key` in place of `private_key` |

After all six, the daemon still holds exactly the one peer that was issued. The
four refusals with the CORRECT bearer are the ones that matter: an attacker who
has the token still cannot revoke every device, rotate the server identity, move
the port, or change routing.

Enforcement is real and asymmetric, not merely labelled. The same privileged pod
manifest, applied to each namespace:

- `agent-stack`: `Error from server (Forbidden)`
- `agent-tunnel`: `Warning: would violate "baseline"` and created

## security-tests.sh

25 passed, 0 failed, 4 noted.

The two failures the previous shape carried are gone, and structurally rather
than by suppression. GOTCHAS 49: a NetworkPolicy selects a POD, so Caddy's
internet egress for ACME was the console's egress too, and the console could
reach a model provider directly. Caddy now lives in a pod that holds no console
and runs no model, so `console -> the model provider` and `console -> the open
internet` both read `blocked, as designed`.

The four notes are unchanged and none is new: etcd encryption unverified without
`--nodes`, an unreadable sshd config on the local host, and two namespaces
(`agent-tunnel`, `default`) where a privileged pod could run. The first of those
two is the exception this whole change exists to isolate, and test 5b audits its
contents rather than merely noting it.

## Not proven here

The passkey ceremony. `console-state` is a fresh volume, so no passkey is
enrolled, and the console falls back to an honest software-signed action record.
The ceremony itself was proven earlier today on the previous shape; what changed
underneath it is the transport, which is proven above. Re-enrolling on this
shape needs a person at a browser.
