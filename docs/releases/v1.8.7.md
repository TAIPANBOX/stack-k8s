# stack-k8s 1.8.7

An agent's tool call that nothing grants now waits for a person, on every new cluster, with nothing to turn on. Model calls pass as they did, and only an explicit grant lifts the hold. A cluster that already runs agents is asked first: the launcher stops before it applies anything and prints what would stop.

v1.8.6 is the tag that built the console this release pins and has no notes of its own: a signature is accepted only from a tag, so the image a release pins comes from the tag before it.

## Upgrade first

1. **Run the launcher and read what it prints.** Before its first apply it puts the cluster's recorded decisions to the policy this run would serve, as a Job of the pinned wardryx that reads the events claim read only. If an agent outside the seeds would be held, or the history could not be asked, the run stops with the agent, the tool, the count and when last, and applies nothing. To go on, move the cluster first, then grant, then turn it on:

   ```bash
   TOOL_HOLD=0 ./deploy.sh <your flags>
   ./tool-hold/agents.sh agent-allow <agent> <tools> --why 'what it is for'
   TOOL_HOLD=1 ./deploy.sh <your flags>
   ```

   `TOOL_HOLD=0` alone leaves the hold out, and the cluster keeps that word. `kubectl apply -k manifests/` by hand leaves it out too: the launchers write the floor, because they are the ones that asked.

2. **Four images move by tag and digest:**

   | Image | 1.8.5 | 1.8.7 |
   |---|---|---|
   | wardryx | v2.5.1 | v2.6.0 |
   | tokenfuse (gateway, MCP broker, `focus-export`) | v1.22.0 | v1.23.0 |
   | tokenfuse-control-plane | v1.22.0 | v1.23.0 |
   | genaryx-console (the console, `quality-drift`, `verdryx-slo`) | v1.8.4 | v1.8.6 |

3. **wardryx changes its schema at its first start on 2.6.0, with no step of yours.** The table `approvals` gains a nullable column, `pending_key`, and two partial indexes, `approvals_pending_call` (unique, on agent, run and key, over pending rows that have a key) and `approvals_pending` (on agent and time, over pending rows). `WARDRYX_DB` is set on every cluster, so every cluster takes this step. Writes to `approvals` wait for the index build, that one time. Existing rows have no key, so they sit outside the unique index and nothing can conflict. A rollback leaves the column and the indexes in place, and 2.5.1 neither reads nor writes them.

4. **A page that hides text in Unicode tag characters or bidi isolates now raises `suspected_injection`.** The gateway runs the firewall in `enforce`, so a run that reads such a page can lose tools it had before.

5. **A held tool call says why.** The `-32004` refusal now reads `requires approval (approval <id>) (<reason>)`. A client that matched the old text exactly must match the new one.

## What changed

- **The floor.** `wardryx-tool-hold`, a ConfigMap of its own that wardryx's policy directory projects, carries `target: "*"` with `when_no_grant: hold`, so an agent id with no `agent://` scheme cannot walk past it. Its body is stack-single's, rule for rule.
- **The seeds.** `grant-drills` gives the fire drills every tool, and their own deny rules still apply. `grant-install-check` gives one id one tool under the broker's static key. `grant-operator-web` gives the operator `fetch_url` and `browse` where a scopyx runs. Felyx and CostCrew get nothing: both make model calls only.
- **The switch.** `TOOL_HOLD` or `--tool-hold`, on all three launchers. `0` takes the block out and leaves the ConfigMap empty, and a run that says nothing keeps it so. `1` turns it on over whatever the question found.
- **Three commands.** `./tool-hold/agents.sh agent-allow`, `agent-deny` and `agent-list` are stack-single's, for a cluster. A grant goes through `PUT /v1/policies`, in force at once with no restart and on the record as `policy_updated`. The request runs in the console's pod, so the admin key stays where the Secret put it and is on no command line.
- **The console** shows a person's grant as the raw approval token, once (genaryx#151).
- **A rule a restriction cannot lift.** Only a grant on a target that names a trust domain lifts the hold. A `deny_tool`, a `max_steps` or a signal rule changes nothing about it.

## Going back

`TOOL_HOLD=0` first, and only then an older tree or image. A wardryx older than 2.6.0 refuses `when_no_grant` and `grant_tool` at load, and an enforcement point that fails closed then refuses everything. By hand: delete the ConfigMap `wardryx-tool-hold`, then `rollout restart deployment/wardryx`.
