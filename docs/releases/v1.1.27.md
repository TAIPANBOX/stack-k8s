# stack-k8s 1.1.27

tokenfuse moves to `v1.6.0`. This turns on the hub-entry route that 1.1.26
shipped ahead of it. One fix merged since 1.1.26 ships with it.

## What moves

- **tokenfuse `v1.5.0` -> `v1.6.0`**: `tokenfuse-control-plane`, the gateway,
  its `focus-export` sidecar and `tokenfuse-mcp-broker`. The tag is v1.6.0 on
  tokenfuse `f342412` and carries tokenfuse#356 and #358.
  - **A remote site remembers what its runs have spent** (tokenfuse#356,
    invariant 75).
    - The Cloud now serves `GET /v1/run-spend`. It answers only a key bound to
      a site, and only about that site's own runs.
    - The hub entry has routed this path since 1.1.26 (#125). From this
      release a remote site's gateway seeds its runs' spend through it after a
      restart or a hub migration, instead of starting every run at zero.
    - In-cluster gateways are unchanged: their key is bound to no site, so the
      route answers 403 and they keep reading `GET /v1/runs`.
  - **The MCP broker speaks streamable HTTP to its upstream** (tokenfuse#358,
    invariant 76).
    - It sends `Accept: application/json, text/event-stream`.
    - It reads an event-stream reply, so an MCP Python SDK server no longer
      answers 406 or a reply it cannot parse.
- **The `TOKENFUSE_MCP_KEYS` example gives a bare key id** (#127,
  invariant 33): the README and the broker manifest's header now give the
  example a bare key id, and a gate holds it.

No other pin moves.

## Measured

Locally on the Mac, 2026-10-05, with release binaries built from tokenfuse#356.
The edge was a stand-in for this repository's hub entry that reads the cloud
route set from `manifests/53-hub-entry.yaml`. The Cloud held `mig-flint` at
21000 uUSD, pushed by site `flint`, and the budget was USD 0.022:

| Gateway after a restart | What happened at the edge | Next call |
|---|---|---|
| The #356 gateway | Seeded the run through `/v1/run-spend` | 402 (`spent_usd 0.021`) |
| The v1.5.0 gateway | Got 404 on `/v1/runs` and seeded nothing | 200 |

At the same edge, `/v1/run-spend` answered 200 to the site key, 403 to an
admin key and 401 to no key; `/v1/runs` answered 404.

## Not proven

- **This exact set on a cluster.** `verify.sh` and `security-tests.sh` were not
  run against it, and v1.6.0 has not been deployed on a cluster from these
  manifests.
- **The real hub entry.** It was not exercised: no Caddy carrying the eighth
  route, and no live hub.
- **#358.** It was proven in its own PR against MCP Python SDK servers, not
  through this stack.
