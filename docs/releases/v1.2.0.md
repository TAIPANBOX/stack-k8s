# stack-k8s 1.2.0

Minor, not a patch: the agent-token audience moves, heraldyx refuses a mail server without STARTTLS by default, and
the bus readers gain a supplementary group.

It covers everything since v1.1.48: pull request #187 (stream files are created by their writers) and pull
request #188 (the image pins move to the 2026-10-17 agent-security wave, with the conflicts that check found). It
tags nothing: the tag is a separate step, taken after the pull requests are merged.

## Upgrade

Read this before you apply the manifests to a running cluster. Items 1 to 3 need an action or a decision. Items 4
to 7 change what you set or expect.

1. **The agent-token audience moved, if the agent-token door is on.** The gateway door, the MCP broker door and
   vouchryx now name one audience, `https://vouchryx.agent-stack.invalid`. They named `http://vouchryx:4310`
   before. tokenfuse v1.17.0 and later refuse a broker whose agent audience is not an absolute https URL, so the
   broker would not start on that tokenfuse with the old value. Run `kubectl apply -k manifests/`, then run
   `./agent-tokens/up.sh` again: the door patches are not in the default apply, so only that script moves them.
   An agent asks vouchryx with RFC 8707 `resource=https://vouchryx.agent-stack.invalid`, and a request that names no
   resource is refused `audience_not_allowed`: vouchryx does not fall back to its own issuer (`internal/api/agents.go`
   at v0.6.0; measured in `evidence/agent-tokens-kind/`, `output-v1.18.0.txt`). The workload audience, the one a pod's
   projected service-account token carries, did not change, and stays `http://vouchryx:4310`.
2. **heraldyx 0.8.0 refuses a mail server that does not offer STARTTLS.** The default is `starttls`. A server on
   port 465 needs `HERALDYX_SMTP_TLS=implicit`, and `plain` is allowed only for a loopback relay. Set the variable
   in your environment and run your deploy script again (`deploy.sh`, `cloud/aws/deploy-aws.sh` or
   `cloud/gcp/deploy-gcp.sh`); the script checks the word and writes it into the `heraldyx-mail` Secret. Without
   the key the notifier stays on `starttls`.
3. **Apply the manifests in one run, because the bus readers now need group 10001.** idryx, the identity sweep and
   heraldyx carry `supplementalGroups: [10001]`, and the bus writers create their stream files in group 10001 (item 4).
   A reader that has not rolled out yet cannot read a file a writer has just created at mode 0640. `kubectl apply -k
   manifests/`, then `./agent-tokens/up.sh` if you run the door, rolls them together. Nothing else to change.
4. **Stream files: new ones are 0640, and each writer creates its own.** agent-stack-go v2 creates a missing stream at
   mode 0640, and only in a directory its own uid owns, and the volume roots belong to root. So each writer's pod now
   has an init container, `precreate-streams`, that creates its file as the writer's uid before the writer starts
   (#187; see below). An existing file keeps its mode and owner and is opened as it is. The journal heraldyx keeps
   on its own volume (`sent.ndjson`) is created the same way (#188, GOTCHAS 136).
5. **The delegation plane's trusted issuers are yours, and change nothing here.** vouchryx 0.5.0 and later refuse a
   subject token that carries no `cnf.jkt`, unless its issuer line ends in `|unbound`. The line in the
   `vouchryx-trusted-issuers` ConfigMap is the one you gave `delegation/up.sh`, and this release does not rewrite it.
   If that line came from the demo IdP (`vouchryx-demo keygen`), it must end in `|unbound`. Never add `|unbound`
   to `VOUCHRYX_WORKLOAD_ISSUERS`: vouchryx refuses to start with it there.
6. **The Keyryx overlay sets a deadline for v2 approval tokens.** With the Keyryx signer on, wardryx 2.2.x verifies a
   v2 HMAC approval token only until `WARDRYX_APPROVAL_V2_UNTIL`. `keyryx/up.sh` sets that to one hour after its
   first run, and keeps an existing value on a re-run, so a re-run does not extend the window. Holds granted before
   the switch return to a person after the deadline.
7. **The images are digest-pinned as before, and their signatures are in the legacy `.sig` format.** Each
   TAIPANBOX image this repository names has a legacy `.sig` tag, probed on the registry on 2026-10-19 (see
   `policy/README.md`). Nothing to do. The admission policy stays opt-in, and whether it admits these digests is not
   measured yet.

## Changes since v1.1.48, by pull request

### #188: the 2026-10-17 agent-security pin move

The image pins move to the releases of the wave, and the conflicts the wave's check found for this launcher are
closed or marked not applicable. The release notes above carry the operator-facing part; this is the record.

- **Agent-token audience** (item 1). One https identifier on the gateway door, the broker door and vouchryx's
  allowed audiences. `scripts/agent-tokens-are-wired.sh` checks the three against each other and against the example
  agent's `VOUCHRYX_AGENT_RESOURCE`, and the teeth cover each. GOTCHAS 137.
- **Broker taint key.** Closed by the existing configuration: the door patch that turns the door on sets
  `TOKENFUSE_MCP_TAINT_GATEWAY_KEY_FILE` from the `broker-taint-key` Secret, and `agent-tokens/up.sh` refuses to turn
  the door on without it.
- **Operator's trusted issuers.** Documentation only (item 5).
- **vouchryx's Keyryx signer root pin.** Not applicable: no launcher sets `VOUCHRYX_SIGNER`.
- **heraldyx STARTTLS.** `HERALDYX_SMTP_TLS` is read by the three deploy scripts, checked before anything is installed,
  and written into the `heraldyx-mail` Secret; the manifest reads it as an optional key (item 2).
- **heraldyx journal.** heraldyx keeps `sent.ndjson` on its own volume, and an event writer cannot create it on a fresh
  claim. It now has the same init container as the bus writers. Without it the notifier logs the error and sends mail
  with no record of it. Measured with `evidence/heraldyx-journal-kind/run.sh` (output beside it). GOTCHAS 136.
- **Keyryx overlay approval deadline.** `WARDRYX_APPROVAL_V2_UNTIL` is set when the overlay is applied (item 6).
- **Writers the table lacked.** heraldyx is one. `qryx` writes a stream only with `--events`, which the crypto-trend
  job does not pass. `idryx` writes a stream only with `IDRYX_EVENTS`, which no manifest sets, and its bus mount is
  read-only; `identity-sweep` is the same shape. Neither needed a writer entry.
- **costcrew analyst ids.** This repository already pins costcrew 0.8.0, and its identity map binds
  `agent://<trust domain>/costcrew/*`.
- **XAA on the agent door.** No launcher turns it on.
- **`stack-caddy` and `stack-wg`.** No manifest names them. The tunnel builds them locally (`tunnel/`), and
  `tunnel-images.yml` publishes the released ones.
- **trailryx 1.3.x and agent-conform's schema v1.0.** The record seal reads every `*.ndjson` on the bus, including
  `agent-conform.ndjson`, and trailryx 1.3.x counts that schema as unknown. The wave's check does not count this as a
  blocker. It was not re-measured for this release.

### #187: stream files are created by their writers, and the readers gain group 10001

agent-stack-go v2 refuses to create a missing stream in a directory another uid owns, and the volume roots belong to
root, so a writer with no file yet exited at start: wardryx v2.2.1 exited 1 and agent-conform v2.0.1 exited 2 on an
empty volume. Each writer's pod now has an init container, `precreate-streams`, that runs busybox pinned by digest as
the writer's own uid, sets `umask 027`, and creates the file only when it is absent, in group 10001. Pods covered:
wardryx, the drills (mockryx), agent-conform, scopyx (its own journal), costcrew (the service and the crew CronJob),
typryx, and vouchryx (its event log and its revocation list). The readers of the bus files, idryx, the identity sweep
and heraldyx, carry `supplementalGroups: [10001]`. Pod Security `restricted` admits all of it without a root step.

- **Gate:** `scripts/stream-files-are-precreated.sh` (CLAUDE.md invariant 59, GOTCHAS 135), in both callers, with the
  teeth it was red on before the manifests changed.
- **Measured:** `evidence/stream-precreate-kind/` on kind v0.33.0 (Kubernetes v1.37.0), 2026-10-19: the unfixed wardryx
  and agent-conform pods exit 1 and 2, refused for want of a file; with the init containers, wardryx is Ready and
  agent-conform exits 1 with one `chain_broken` alert written.
- **Policy:** `evidence/verified-images-kind/admission-v1148.sh` measured the admission policy on kind with
  policy-controller v0.15.1: the three v1.1.48 TAIPANBOX digests were admitted, and the v1.1.47 genaryx-console was
  refused with "no signatures found".
- **Test harness.** The teeth harness's needle check piped `printf` into `grep -q` under `pipefail`, so a found needle
  could read as a wrong reason. It uses a here-string now. This is test-only.

#187 moved no image pin, and it does not change the mode of a file that already exists.

## What does not apply, and why

These are the checks the pin move ran that found nothing to do in this launcher. A later reader should not re-derive
them.

- `TOKENFUSE_MCP_RESOURCE` and XAA on the agent door: no launcher sets either (tokenfuse v1.17.0's same-resource rule).
- `VOUCHRYX_SIGNER=keyryx` and `VOUCHRYX_KEYRYX_ROOT_PIN`: no launcher sets `VOUCHRYX_SIGNER` (vouchryx 0.6.0).
- costcrew 0.8.0 analyst ids: already in place in this repository.
- `stack-caddy` and `stack-wg` at v1.1.48: no manifest names them.

## Not measured

- No cluster run of this release. The gates in `CLAUDE.md` run locally on the release commit; the teeth run is in the
  pull request.
- The agent-token door was measured on kind with stand-ins for the provider, the MCP upstream, the gateway and broker
  base, and the network rules (`evidence/agent-tokens-kind/output-v1.18.0.txt`). Not run: a real k3s issuer, the
  workload path, and a ban that must survive a vouchryx restart on a volume.
- Whether the admission policy admits the new digests: their signatures are present and verify with cosign v3.1.3, but
  no admission run was made with them.
