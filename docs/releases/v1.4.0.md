# stack-k8s 1.4.0

A minor, not a patch, and breaking for cloud deploys. The cloud launchers now verify each node's SSH host key before they connect, and refuse a node whose key they cannot read or do not match. Cloud deploys turn admission on, so an operator's agent images must be listed before the deploy. Every installer keeps secret values off the command line. Without `SSH_KNOWN_HOSTS`, `install.sh` and `deploy.sh` still accept a host on its first connection, as before, and now print each key they accept.

It covers everything since v1.3.0: pull request #190, four commits, one per part, each checked as its own state. The tag is a separate step, taken after the pull request is merged.

## Upgrade

Read this before you run a cloud deploy again. Items 1, 2 and 7 need an action or change what a cloud deploy requires. Items 3 to 6 add an option, change how a Secret is written, or correct an earlier note.

1. **The cloud launchers verify SSH host keys before they connect.** `cloud/gcp/deploy-gcp.sh` and `cloud/aws/deploy-aws.sh` read each node's host keys out of band before the first connection, and connect only with those keys. On GCP the keys come from the instance's guest attributes, so the deploy machine needs `gcloud` with permission to read them. On AWS the keys come from the fingerprints cloud-init prints to the console, so the deploy machine needs `aws ec2 get-console-output`. A node that does not publish its keys within 300 s stops the deploy with the reason. A node whose keys do not match the console fingerprints is refused at once, and so is a node whose keys cannot be read at all. Migration: run the deploy from a machine where `gcloud` or `aws` can read those, and expect a cloud-init that prints no fingerprint block to fail the deploy after 300 s.

2. **Cloud deploys turn admission on.** After the apply, `cloud/gcp/deploy-gcp.sh` and `cloud/aws/deploy-aws.sh` run `policy/up.sh --enforce` on the first node, as `deploy.sh` does. From then on a new pod in agent-stack is admitted only when its image verifies: a TAIPANBOX image under its own repository's signature, an upstream image pinned by digest and listed, or an operator image listed in the operator policy. Migration: before you deploy, copy `policy/operator-image-policy.example.yaml` to `policy/operator-image-policy.yaml` and list each agent image there, by digest for an unsigned image, or with the keyless identity or the public key that signs it. `policy/README.md` has the templates. The copy is not in git. A cloud cluster deployed by 1.3.0 is not admitted until you run `policy/up.sh --enforce` on it by hand, once. The step is repeatable.

3. **`SSH_KNOWN_HOSTS=<file>` pins your own hosts.** `install.sh`, `deploy.sh` and `security-tests.sh` connect strictly against the host keys in the file it names. The variable is optional. Without it, `install.sh` and `deploy.sh` accept each host on its first connection, as before, and print each key they accept with the line that pins it. Migration for bring-your-own servers: write your servers' host keys to a file, and set `SSH_KNOWN_HOSTS` to its path.

4. **Secrets are created from a manifest on stdin.** Installers and launchers create their Secrets with `kubectl create -f -`, reading the manifest from stdin, so no secret value is on a command line. Existing Secrets are not rewritten by any path in this release. Migration: none. A re-run does not replace a Secret's value.

5. **`deploy.sh` gives the Hetzner token to `install.sh` in the environment.** `deploy.sh` passes `HCLOUD_TOKEN` to `install.sh` as an environment variable, not as a flag. `install.sh --token` still works when you run `install.sh` directly. Migration: none.

6. **The 1.3.0 note on admission is corrected.** Item 3 of `docs/releases/v1.3.0.md` said the cloud deploy scripts did not turn admission on in 1.3.0. That is right for 1.3.0, and 1.4.0 turns it on (item 2 above). `policy/README.md` says the same. A cloud cluster deployed by 1.3.0 still needs the hand run in item 2.

7. **The image distribution between nodes checks each peer against the verified keys.** `deploy.sh`, `cloud/gcp/deploy-gcp.sh` and `cloud/aws/deploy-aws.sh` write `/root/.ssh/stack-known-hosts` on the builder (mode 0600) before the builder's first ssh to a peer, and the builder connects strictly against that file. The builder is the last node in the node list. Each node is named by its public and its private address, with the key the launcher verified. No tracked script disables host key checking any more. Migration: a node added outside the launcher, or a node whose key the launcher did not verify, now fails the distribution with the reason, and the rest of that deploy does not run. Add nodes through the launcher so that their keys are verified.

## Changes, by area

- **Secrets off the command line (invariant 60).** Installers and launchers used to put secret values on command lines: plane credentials in ssh command strings, the k3s and Hetzner tokens as environment assignments on the remote command, bearer headers in curl, a token inside a git clone URL, the instance metadata session token, the tunnel's TLS key as an argument, and a token passed from `deploy.sh` to `install.sh` as a flag. An argument is readable by every user on both ends of an ssh connection for as long as its process runs. Now `lib/secret-doc.sh` builds each Secret manifest with its values base64 encoded, and kubectl reads it on stdin. The k3s and Hetzner tokens are the first line of stdin, read by the far shell. Bearers reach curl through `--config -` or a process substitution. The console clone reads its token through a git credential helper, so its URL carries none. Gate: `scripts/no-secret-on-argv.sh`.
- **Host keys verified before the first connection (invariant 61).** The cloud launchers connected with `accept-new`, so the key a node offered on its first connection became its key for good. `lib/hostkeys.sh` now fills a per-run known_hosts file before any connection. On GCP the keys come from the guest attributes, read through Google's authenticated API. On AWS they come from the fingerprint block cloud-init prints to the console, and a node's keys are kept only when their SHA256 fingerprints are the ones printed. A mismatch is refused at once. A block or a keyscan that is not there yet is retried until a 300 s deadline, then refused with the reason. The four cloud launchers connect with `StrictHostKeyChecking=yes` against that file alone. Gate: `scripts/hostkeys-are-verified.sh`.
- **Image distribution between nodes (invariant 61).** The builder pushed each image to its peers with host key checking off, in `deploy.sh`, `deploy-gcp.sh` and `deploy-aws.sh`. The launcher now writes a peer file from the keys it verified, before the builder's first peer connection, and the distribution connects strictly against that file. The gate also checks that no tracked script carries the option that disables checking, outside prose.
- **Admission in the cloud deploys (invariant 58).** `deploy-gcp.sh` and `deploy-aws.sh` run `policy/up.sh --enforce` on the first node after the apply, through k3s's kubectl, and copy `policy/` to the node with the manifests. `scripts/verified-images-are-enforced.sh` checks the order in all three launchers.
- **Records.** CLAUDE.md invariants 58, 60 and 61 carry their gates. GOTCHAS 139 to 141 hold the traps behind this release, and 141 is the admission measurement named under "Not measured". `scripts/gates-have-teeth.sh` has a case for each new gate.

## Not measured

- No cloud launcher has been run. The guest-attribute JSON and the console fingerprint block were read from their documented fields, not from a live instance. The first live cloud deploy is the first test of item 1.
- No k3s node has run the stdin install (the token read by the far shell, then `sh -s`) or `kubectl create -f -` over ssh with sudo. kind does not run the k3s installer.
- The peer file has not been seen on a live distribution. No run has yet shown a builder reaching a peer's private address with the file the launcher wrote.
- Admission was measured on kind only, with one namespace's egress cut to stand in for a Sigstore outage. A policy controller that had already verified a digest kept admitting its pod while the cut was in place. After a restart the same cut refused it, and so did a fresh signed digest and an unsigned image. The mechanism is inferred from these outcomes, not read from the controller's source. The cache lifetime was not measured. One probe reached Sigstore's TUF CDN while another registry was blocked, and that is not explained (GOTCHAS 141).
- `build.sh` still connects to one named node with the default ssh policy. It is an operator push, not a peer loop, and it is outside invariant 61.
- Secret values staying out of logs and the environment is not claimed.
