# stack-k8s 1.7.2

A patch that moves TokenFuse from 1.20.0 to 1.20.1, a security fix. Before TokenFuse 1.20.1, a JSON-RPC batch sent to the MCP broker skipped every check the broker keys on `tools/call`: the policy decision, the identity requirement, the scan of the arguments and the tool-call record. The broker forwarded the batch to the upstream as it came. TokenFuse 1.20.1 refuses it before anything is forwarded. Upgrading is recommended for every cluster that runs the broker.

## Upgrade

1. **Re-run the launcher, or apply the manifests of this tag.** TokenFuse moves one patch, by tag and index digest (#208):

   | Image | 1.7.1 | 1.7.2 |
   |---|---|---|
   | tokenfuse (gateway, MCP broker, `focus-export` sidecar) | v1.20.0 | v1.20.1 |
   | tokenfuse-control-plane | v1.20.0 | v1.20.1 |

   The gateway image is `sha256:8de459eca2a10ae36a01d0249b91c3b0c62b50b47ad2c4a309e2ea02e0a460dd` and the control plane `sha256:157d5801367674e7af8625b391fba8e26e3b72fe95dcb5e435cebee5555fa92a`. Each is an amd64 and arm64 manifest list and carries a cosign signature in the legacy `.sig` format that policy-controller reads. The gateway image's build provenance names commit `27a0a2f` at `refs/tags/v1.20.1` of TAIPANBOX/tokenfuse. No configuration changes: the door origins of invariant 74 stay as they are.
2. **A client that sends JSON-RPC batches to the MCP broker now gets an error.** The answer is JSON-RPC `-32600` (Invalid Request) with a null id, and HTTP 400. Send each message on its own. The Model Context Protocol removed batching in its 2025-06-18 revision, so a client on the current protocol is not affected.

TokenFuse 1.20.1 also clears five RustSec advisories, among them a timing issue in `crypto-bigint`, by moving its P-256 code to `p256` 0.14 with the wire format unchanged.

## Measured

- CI on #208: fast-gates, gates, secretscan and the four teeth shards green. The first run's teeth found one case whose mutation still named v1.20.0 in a regular expression, so it applied nothing; the same PR fixed it, and the case was also run by hand: the real manifests pass `agent-tokens-are-required.sh`, and the mutation makes it fail as the case expects.
- Each pinned digest was read from the registry before it was written, with its `.sig` tag, and the gateway image's provenance was read.
- The batch refusal ran live on a single-box install (stack-single 1.4.3, forge, 2026-10-26): the same batch that reached the upstream under TokenFuse 1.19.0 was answered with HTTP 400 and `-32600` under 1.20.1, and nothing was forwarded. Agent tokens held 10 of 10 there after the upgrade.

## Not measured

- Nothing in this release was run on a live cluster: no image was admitted by policy-controller, and the broker on Kubernetes did not receive a batch.
