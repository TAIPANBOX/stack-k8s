# stack-k8s 1.1.45

This release puts the policy store on a storage class that keeps a readable replica, and makes
the deploy refuse to touch a cluster whose store is still on the old class. It adds the cost
refusal, and it fixes three things a live drill and the gates found: cluster DNS had one replica
and no budget, a node stopped with its pods running took its network down under a volume writer,
and `security-tests.sh` did not parse on a Mac. It also carries the typed-answer door minting, the
bounded secret generator and the AWS flag parity, and it moves every pin to the release that is
current today.

Merging this release changes no running cluster. What changes, and what does not, is set out in
"What an existing cluster does" below. The tag builds the console image `v1.1.45`; the pin to it
comes in a separate pull request after the tag, as `v1.1.44` did.

## What the tag builds

Pushing the tag `v1.1.45` starts two workflows and nothing else:

- `console-image.yml` publishes `ghcr.io/taipanbox/genaryx-console:v1.1.45`, built for amd64 and
  arm64 from the tag's `images/console.Dockerfile`. Its five source repositories are checked out
  at their default-branch head at build time, not at a pinned commit. When this was written they
  were `genaryx` `2600d3dd79c4`, `qryx` `325e8ef369a5`, `mockryx` `6f62b44a5f5f`, `verdryx`
  `3b243877fe90` and `engram` `c8708c5aa78e`. The image's labels record the five commits it was
  built from, so the build can be checked afterwards.
- `tunnel-images.yml` publishes `ghcr.io/taipanbox/stack-caddy:v1.1.45` and
  `ghcr.io/taipanbox/stack-wg:v1.1.45`.

No other image is built by this repository. The other pins are published by their own repositories.

## Changes, by invariant

**The policy store keeps a readable replica (invariant 43, GOTCHAS 129, #164).** A two-minute cut
of the node that ran the store's engine left every replica of its only volume in error, and
Postgres then refused its own checkpoint. The store's claim now names the `stack-policy` storage
class, which keeps a replica on the store's own node, keeps the revision counter on, keeps a
failed replica for 48 hours and retains its data. The three Longhorn installers create that class.
Before any deploy applies the manifests, `lib/policy-store.sh` refuses a cluster whose policy-db is
on another class, with a sentence that names the migration in GOTCHAS 129. There is no opt-out.

**Cost reports refuse what they cannot price (invariant 44, GOTCHAS 127, #165).** A running
machine type with no published rate now makes `cloud/aws/cost-live.sh` and
`cloud/gcp/cost-live.sh` exit non-zero, name the type and print no total. The AWS table gains
`m7i.xlarge`. The GCP table has no `e2-standard-4` rate yet, so a GCP report on that machine type
refuses until a rate is added with its source.

**Cluster DNS keeps a replica through a drain (invariant 45, GOTCHAS 128, #166).** The installers
scale k3s's coredns to two replicas, or to three from five nodes, and apply a PodDisruptionBudget
(`kube-system/coredns`, `minAvailable: 1`) when there are two or more. `verify.sh` fails a
multi-node cluster with no budget. A node that dies keeps its replica's address in the Service
until it is NotReady, about 50 seconds by Kubernetes' default; that is named in GOTCHAS 128 and is
not removed by this release.

**A node stopped with its pods running stops them first (invariant 46, GOTCHAS 130, #167).** Every
k3s node gets a kubelet drop-in with `shutdownGracePeriod: 60s` and `shutdownGracePeriodCriticalPods:
15s`, and a systemd-logind drop-in with `InhibitDelayMaxSec=180`, both written before k3s starts. A
node that stops its pods this way shows them as `Terminated`, and `verify.sh` notes them by name
and does not count them. Priority bands for Longhorn's managers are not used; GOTCHAS 130 says why.

**`security-tests.sh` parses under the bash a Mac ships (invariant 47, GOTCHAS 131, #168).** macOS
ships bash 3.2, and CI runs bash 5. The script did not parse under 3.2, so sections 10 and later
never ran for an operator on a Mac. Its node checks over `ssh` also read login banners; they now
read only the line their own probe printed.

**Every k3s server is started with `--secrets-encryption` (invariant 48, GOTCHAS 132, #169).** The
installers pass the flag on the first server and on every joining server, and a gate checks each
invocation carries it on a line of code, not in a comment. A cluster built before this release is
not changed by the flag.

**Typed deploys mint their doors (invariant 42, GOTCHAS 126, #162).** The deploy creates
`typryx-keys` and `tokenfuse-mcp-broker-keys` when they are absent and never overwrites them. Before
this, both were documented as made by hand, and a typed deploy stayed Pending.

**The operator password comes from a bounded read (invariant 41, GOTCHAS 125, #161).** The three
deploy scripts use one generator, `lib/gen.sh`, which ends on its own whatever SIGPIPE is set to.

**The AWS deploy takes every flag the GCP deploy takes (invariant 40, #160).**
`cloud/aws/deploy-aws.sh` takes `--copilot-key-file`, read from the file and sent to the node on
stdin.

**Pins and documentation (#163).** The pins in the table above, the teeth needles that name them,
and a README section for `allow_models` (wardryx v1.5.0). The README example of a `hold_if_signal`
rule now sets `when_absent: hold`, and says what that costs and why single-use stays on.

## What an existing cluster does

- Merging changes no running cluster on its own.
- A deploy run against an existing cluster whose policy store is on the old class stops before its
  first apply and names the migration in GOTCHAS 129. The migration is planned, not automatic, and
  it has not been run on a live cluster. Until it is, that cluster cannot be re-applied from these
  scripts.
- The installer changes (DNS budget, node shutdown settings, secrets encryption flag) apply when an
  installer runs. A running cluster that did not go through them needs the steps in GOTCHAS 130 and
  131, and the secrets-encryption steps in GOTCHAS 132, which were not run here.
- Typed deploys keep existing door Secrets and create only the ones that are missing.

## Measured

- The gates in `.github/workflows/gates.yml`, on the release commit, in CI. The run is linked from
  the pull request.
- The index digests above were read with `docker buildx imagetools inspect` on 2026-10-14. The
  wardryx policies were loaded by the pinned wardryx `v1.5.0` through its offline
  `check` command, with the negative controls refused as expected (#163).

## Not proven

- The policy store has not been rerun under a partition on a cluster built from this release, and
  its write-latency cost is not measured. An existing cluster has not been migrated.
- The DNS budget has been measured on a local kind cluster, not on a live multi-node one.
- The node shutdown order has not been measured on a live node with this release's settings.
- Secrets encryption on an existing cluster has not been applied; GOTCHAS 132 says why and how.
- `e2-standard-4` has no GCP rate in the cost script yet.
