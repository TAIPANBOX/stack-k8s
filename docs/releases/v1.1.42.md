# stack-k8s 1.1.42

Wardryx moves to `v1.3.0`. A policy can now name the only tools its agents may
use, and `deny_tool` also reads the tool name inside a request's tool call. A
policy that uses neither change decides as it did before and keeps its
`PolicyVersion`.

## What moves

- **Wardryx `v1.2.0` -> `v1.3.0`** (`manifests/10-planes.yaml`, the `wardryx`
  Deployment). Release notes:
  [wardryx v1.3.0](https://github.com/TAIPANBOX/wardryx/releases/tag/v1.3.0).
  - **`allow_tool`.** A policy may carry the list of tools its agents may use.
    A tool the list does not name is denied, and a renamed tool is denied too.
    No approval lifts that denial. When several matching policies set a list,
    a tool must be named by each of them. An empty or absent list restricts
    nothing.
  - **`deny_tool` reads the tool call's name.** A request that names a denied
    tool only inside its `tool_call` is now refused. Before this release, only
    the request's own tool list was read.
  - **No caching under these rules.** A decision under `allow_tool`, and under
    `deny_tool` for a request that carries a tool call, is never cacheable. Such
    a policy costs one policy round trip per call.

No other pin moves.

## Upgrading

- **A policy that uses neither change keeps its behaviour and its
  `PolicyVersion`, with one exception.** A request whose `tool_call` names a
  tool on a `deny_tool` list, while the request's own tool list does not name
  it, was allowed before and is denied now. A caller that puts the same name in
  both places sees no change.
- **This launcher seeds no `allow_tool` policy.** The seeded policy file is
  `wardryx-policy` in `manifests/00-base.yaml`. It holds two starter policies,
  both for `agent://mockryx.local/*`: one holds calls costing more than 1 USD
  for a person, and one denies `shell_exec`. Neither uses `allow_tool`.
- **Rollback trap.** A policy stored through `PUT /v1/policies/{id}` with
  `allow_tool` is silently stripped by a build older than v1.3.0, and that
  build then no longer restricts the agent's tools by that list. A policy file
  with the field fails loudly on an older build, at start, with
  `field allow_tool not found`. Before pinning back to v1.2.0, remove
  `allow_tool` from every stored policy.

## Not proven

- **No live run of v1.3.0 on this launcher.** Nothing here was started on a
  cluster, and `verify.sh` and `security-tests.sh` were not run.
- **What CI covers.** This repository's CI runs the offline gates and the
  `uapi-proxy` tests. No CI leg installs the stack or starts the wardryx image,
  so CI does not run v1.3.0 end to end.
- **Wardryx's own open items.** Its release notes list what they did not run,
  including an end-to-end rollback on an older build, and a live enforcement
  point sending `allow_tool` policies.
- **Decision caches.** Whether this launcher's gateway caches wardryx decisions
  was not checked. A caller that caches must key on whether a tool call is
  present, because a request with no tool call under `deny_tool` stays
  cacheable.
