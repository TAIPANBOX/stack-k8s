# stack-k8s 1.1.13

A second site can now report to this cluster over the internet, with no VPN,
and the hub can tell a quiet site from a dead one.

## What changed

- **One narrow public entry for a remote site (#107, invariant 23).**
  `manifests/53-hub-entry.yaml` is opt-in and outside the default apply:
  Caddy in front, TLS from a free Let's Encrypt certificate, exactly the
  seven routes a remote gateway calls, and 404 for everything else, the
  console included. `hub/up.sh` applies it and prints the two URLs,
  `hub/add-site.sh <name>` mints one site's two keys into a 0600 env file,
  and `hub/down.sh` deletes the load balancer first. README, "A second site".
- **TokenFuse 1.3.0 (gateway, `focus-export`, the MCP broker and the control
  plane).** An idle gateway now sends the Cloud a heartbeat every 30 s
  (`TOKENFUSE_CLOUD_HEARTBEAT_SECONDS`, `0` turns it off), so a remote site
  with no traffic stays visible on `GET /v1/gateways` instead of going quiet
  like a dead one. TokenFuse's own notes: `docs/releases/v1.3.0.md` in that
  repository.

## Measured

On 2026-09-27, a hub of three VMs on GCP and a k3d cluster at home as the
remote site, both from the branches these releases were cut from:

| | result |
|---|---|
| `deploy-gcp.sh`, then `hub/up.sh` | 12 min 14 s, verify.sh 16/0/1, security-tests.sh 27/0/3; the entry with both certificates in 66 s |
| the entry from the internet, with the site's own key file | 16 of 16 as intended: the site's polls and ingest 200, no key 401, the console and every other route 404 at the edge |
| the home site's gateway given the four variables | its calls decided by the hub's policy plane; the hub names the site from its key |
| the home site idle, without the heartbeat | last push aged from 34 s to 286 s in four minutes |
| the home site idle, with it | one push about every 31 s, last push never older than 22 s |

The images on the home site were built from the pull request, not the
released `tokenfuse:v1.3.0`.

## Upgrade

`kubectl apply -k manifests` rolls the gateway and the control plane once.
The entry is applied only by `hub/up.sh`; a cluster that does not run it
publishes nothing new.

## Not in this release, said plainly

- The released images of this set have not run on a cluster yet.
- The entry was run on GCP only. On AWS the load balancer has no fixed IPv4
  address, so `hub/up.sh` needs `--host` there; untested.
- A site that goes silent is visible on `/v1/gateways` and raises no
  incident.
- Certificate renewal and a second real customer site were not exercised.
