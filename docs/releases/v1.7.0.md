# stack-k8s 1.7.0

The Keyryx witness's findings now reach the notifier and the console. They are delivered read only, through the witness's own claim, with no new volume, and heraldyx is pinned to the release that reads them safely.

## Upgrade

1. **heraldyx is pinned at v0.8.1 by digest** (`sha256:879211d785fc5edaae1ce88d09c82aa8258df31933bf16fb21a661abd28240d3`). An `HERALDYX_EVENTS` entry ending in `.ndjson` is read only while it is a regular file. heraldyx opens every stream without following a link and without waiting on a FIFO. `scripts/bus-names-match-the-source-rule.sh` requires 0.8.1 or later for `keyryx.ndjson`. Do not pin an older heraldyx with this release (invariant 30).
2. **The witness's findings reach heraldyx and the console through the witness's own claim.** The witness writes `alerts/keyryx.ndjson` on `keyryx-witness-state`. Its startup step creates `alerts/` (0750) and the file (0640, group 10001) before it starts.
   - Each reader mounts only `alerts/` of that claim (`subPath`), read only on the mount and on the claim. A reader never sees `data/`, where the witness key lives, and the kubelet does not apply the reader's `fsGroup` to the witness's files.
   - Each reader names the file itself: `HERALDYX_EVENTS=/var/lib/stack/events,/var/lib/keyryx-findings/keyryx.ndjson` and `GENARYX_EVENTS_EXTRA=/var/lib/keyryx-findings/keyryx.ndjson`.
   - The claim is ReadWriteOnce, so each reader is pinned to the witness's node, as the record seal is. Expect heraldyx and the console to move to the node the witness runs on.
   - No new claim is added, and the default manifests do not change (invariant 75).
3. **The readers' wiring is two patch files**, `keyryx/heraldyx-findings-patch.yaml` and `keyryx/console-findings-patch.yaml`, each with an unpatch.
   - The Keyryx install step applies them after the apply. heraldyx is patched only once it is installed, and each deploy script patches it again right after it applies `45-heraldyx.yaml`.
   - `--without-keyryx` reverses both. `keyryx/down.sh` also reverses both before it deletes the witness, so no reader is left pinned to a witness that is gone.
   - If you apply `45-heraldyx.yaml` by hand on a Keyryx install, re-run the launcher afterwards: a fresh apply puts `HERALDYX_EVENTS` back to the bus alone.
4. **The witness's `stack-events` volume is read only on the claim as well as on the mount**, so a container added to the witness later cannot write the bus it witnesses.
5. **The console image `genaryx-console:v1.7.0` is built by this tag** from genaryx #134 (`869c1ce`). That image reads `GENARYX_EVENTS_EXTRA` and turns a witness finding into an incident. The manifests in this release still pin `genaryx-console:v1.6.0`, which ignores the variable. Until the v1.7.0 pin follows in a later change, the findings reach heraldyx's mail and not the console.

## Not in this release

- The console pin to `genaryx-console:v1.7.0`. Its digest exists only after this tag's image build, so the pin follows in the next change.

## Not measured

- Nothing in this release was run on a live cluster. In particular:
  - no patch was applied to a running Deployment, and no finding was mailed or shown;
  - that Longhorn mounts the witness's ReadWriteOnce claim read only into a second pod on the same node while the witness holds it (the record seal relies on the same, also unrun);
  - a reader's `subPath` mount when `alerts/` does not exist yet (the install patches the readers only after the witness has rolled out);
  - a reader that cannot be scheduled while the witness is down.
- The witness owns `alerts/`, so against a file it plants there, what holds is the readers' own checks: heraldyx v0.8.1's regular-file rule, and the console's per-stream source check from genaryx #134.
- Every gate in this release runs on static text and stub binaries. None of them ran a cluster.
