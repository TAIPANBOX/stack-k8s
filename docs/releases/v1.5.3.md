# stack-k8s 1.5.3

A patch. In 1.5.0 to 1.5.2 no k3s agent joined a cluster: every multi-node deploy with agents, on GCP, AWS or your own servers, came up with the servers alone and then waited on Longhorn, with no error. Nothing else changes: no manifest, no pin, no default.

## Upgrade

Nothing to do on a running cluster that has its agents. A cluster deployed by 1.5.0 to 1.5.2 with agents has none joined: run the deploy from the 1.5.3 checkout with the same flags, on the same nodes; it joins them.

## What changed

- **The agent's name is read before the token and the install script are sent.** The agent loop built its command with a substitution that ran its own ssh to the node, and that ssh read the cluster token and the k3s script off the pipeline's stdin, so the agent install ran with neither and exited 0. The installers read the name first, as the server loop already did. GOTCHAS 149.
- **An agent that never registers stops the deploy.** Each agent is waited for by its name, and after 200 s the deploy stops and says the agent did not register, instead of continuing into a wait that names the wrong cause.
- Gate `scripts/stdin-is-read-once.sh` (invariant 64): no stdin-fed remote command runs a remote lookup in its own command string, in every installer and deploy script, and every agent-joining script stops on an agent that does not register. Red first on 1.5.2 with six problems. Five teeth cases, two scenarios.

## Measured

- GCP, 2026-10-19, stack-k8s 1.5.0, one server and two agents: neither agent joined, and the deploy printed no error. The same pipeline run by hand, with nothing else reading its stdin, installed the agent.
