# stack-k8s 1.1.41

The gateway on this launcher runs TokenFuse's agent firewall in `enforce` by default. Until
now every gateway this launcher started ran it in `shadow`, which refuses nothing and only
records what it would have refused. One switch sets the mode back when an operator wants it.

## What moves

- **The gateway's mode.** `manifests/10-planes.yaml` sets `TOKENFUSE_FIREWALL=enforce` on the
  `tokenfuse-gateway` container. The TokenFuse image does not move: this release is still
  `tokenfuse:v1.11.0`.
- **`--firewall enforce|shadow|off`** on `deploy.sh`, `cloud/gcp/deploy-gcp.sh` and
  `cloud/aws/deploy-aws.sh`. `firewall/mode.sh` checks the word before anything is installed,
  and the mode is set after the manifests are applied, which is the only place it sticks.
- **The gate.** `scripts/firewall-is-enforce-by-default.sh` runs in CI and in the pre-push hook.
  It fails when a gateway start lacks the literal `enforce`, when the validator accepts a word
  the gateway ignores, and when a deploy path checks the mode after its first apply.

## What enforce refuses now, and did not before

- A later exec, write or egress call by a run that read untrusted input. The starter policy
  names web, email, file and secret sources. In shadow the same call was recorded and let
  through.
- A run that a declared tool has labelled. A tool declared in a request whose description
  carries a high or critical injection finding labels the run `suspected_injection`. The request
  itself is not refused for that text. The starter rule then applies to the run's later tool
  calls.
- The anti-exfiltration floor stays on in enforce, whatever a policy file says.

## What it does not change

- A run that has read no untrusted input and has no labelled tool is not refused by the firewall
  in either mode.
- The MCP broker and the `focus-export` sidecar carry no switch. The broker asks the gateway
  before it forwards a tool call, so the gateway's mode decides for the broker too.
- The run budget ceiling, the typed-answer modes, and every other manifest value.

## The one switch back to shadow

```bash
./deploy.sh --servers ... --hcloud-token ... --trust-domain acme.example --firewall shadow
```

Give the flag on every run. `kubectl apply -k` puts `enforce` back over a value set by hand, and
a re-run without the flag returns the gateway to `enforce`.

## Upgrade notes

- An existing cluster rolls its gateway once when these manifests are applied, because the pod
  template gains the variable.
- A run that was admitted in shadow and has since read untrusted input can be refused on its next
  call. An operator who needs the old behaviour while reviewing the policy's records passes
  `--firewall shadow` on the same run.

## Not proven

- Measured on a local test stack, not on a live deployment. Test-stack figures: pending, to be
  filled in from the test run.
- That a running gateway refuses a call under enforce. TokenFuse's own test suite covers the
  refusal, and this launcher did not run a cluster to show it.
- That a rolling update leaves no call in an unexpected state while the mode changes.
