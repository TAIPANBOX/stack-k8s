# stack-k8s 1.1.35

TokenFuse moves to `v1.9.0` and the console to `genaryx-console:v1.1.34`, the
two releases that make closing a retained reservation (invariant 36) work end
to end.

## What moves

- **TokenFuse `v1.8.0` -> `v1.9.0`** (`manifests/10-planes.yaml`: the control
  plane, the gateway and its `focus-export` sidecar;
  `manifests/52-tokenfuse-mcp-broker.yaml`). Release notes:
  [tokenfuse v1.9.0](https://github.com/TAIPANBOX/tokenfuse/releases/tag/v1.9.0).
  - **A retained reservation survives a restart.** A call the provider may
    have billed but the gateway could not settle is journaled under the
    gateway's data directory and put back at startup. A journal that exists
    and cannot be read stops the gateway (exit 2) instead of serving as if
    nothing were owed.
  - **It can be closed with evidence**, `POST /v1/retained/close` and
    `GET /v1/retained` behind the admin key, only when
    `TOKENFUSE_CLOSURE_SECRET` is set. `closure/up.sh` sets it; nothing in the
    default apply does.
  - **An observed closure reaches the Cloud** the way a settled call does.
  - **The Cloud no longer accepts the fixed development key**, and
    `TOKENFUSE_CLOUD_ALLOW_DEVKEY` now stops it at start. Nothing here sets it.
- **Console `v1.1.25` -> `v1.1.34`** (`manifests/20-console.yaml`, the
  `quality-drift` CronJob in `manifests/40-routines-and-secrets.yaml`, and
  `security-tests.sh`), built by tag v1.1.34 from genaryx `2317d80`
  (genaryx#91 to #105).
  - **`money_close_retained`**: an admin closes a retained reservation with
    evidence after a passkey assertion; the console mints the token the
    gateway verifies. On with `closure/up.sh`.
  - **A refusal for identity is filed under the key that made the call**, not
    the agent it claimed, in the statistics, the incident centre, Agent 360,
    the delegation graph and Felyx's cost reads.
  - **Felyx counts a reasoning model's output the way the provider bills it.**
  - Eight Dependabot alerts closed; the live tests stop sending the devkey.

No other pin moves.

## Measured

On Docker Compose, 2026-10-12, with the published `tokenfuse:v1.9.0`,
`tokenfuse-control-plane:v1.9.0` and `genaryx-console:v1.1.34` and a stub
provider: `evidence/closure-e2e/run.sh`, 29 of 29, twice from empty
(`evidence/closure-verified.md`). A console closed a retained reservation with
an observed 4321 micro-USD: the gateway settled exactly that, released the
reservation, and the control plane counted it once; a second close was refused
`already_closed`. A no-charge closure settled nothing. A console holding a
different secret was refused by the gateway. After a gateway restart the one
open reservation was still retained and the closed ones were not. With
`GENARYX_WEB_REQUIRE_PASSKEY=1`, as `20-console.yaml` sets, the close was
refused before it reached the gateway.

## Upgrading

- **Nothing to configure** for a cluster that does not close reservations.
- **To turn closing on**, run `closure/up.sh` after this apply. It mints the
  one secret into `closure-keys` and patches the gateway and the console.
- **If anything sets `TOKENFUSE_CLOUD_ALLOW_DEVKEY`** on the control plane,
  remove it first: v1.9.0 refuses to start with it.

## Not proven

- **This exact set on a cluster.** Neither image has been deployed from these
  manifests, and `verify.sh`, `security-tests.sh` and `closure/up.sh` were not
  run against a cluster.
- **A closure against a live provider bill.** The run above used a stub
  provider.
- **The unit half.** No identity map was configured, so no unit reservation
  was retained or closed.
- **The passkey ceremony end to end.** The run used the console's documented
  no-passkey fallback for the close and showed the refusal with
  `GENARYX_WEB_REQUIRE_PASSKEY=1`; the ceremony itself is held by genaryx's
  router tests.
