# stack-k8s 1.5.0

A minor release, and breaking. The default install now requires an agent's own token at the two doors that
take agent calls (the gateway and the MCP broker), admits a static client key only from a named list, and has
wardryx check the token and its proof itself. vouchryx, the service that issues the token, is in the default
install and runs without an identity provider. The component pins move to the releases of 2026-10-19.

It covers everything since v1.4.0 on the launcher branch `feat/require-agent-tokens`. The tag is a separate
step, taken after the pull request is merged. This note is written before the tag exists.

## Upgrade

Read this before you deploy 1.5.0 over a running cluster. Items 1, 2 and 3 change what a running cluster
does. Item 4 is a file you must keep. The rest are notes on a pin.

1. **Static keys not on the list are refused.** With `TOKENFUSE_AGENT_TOKENS=require`, the gateway admits a
   static client key only when its id is on `TOKENFUSE_AGENT_TOKENS_STATIC_KEYS`. The list is `felyx,agents,drills,costcrew,broker`
   (set in `manifests/10-planes.yaml`), and the broker's is `broker-caller` (`manifests/52-tokenfuse-mcp-broker.yaml`).
   A client that holds another key gets `401 agent_token_required`. To keep one, add it to the ConfigMap
   `gateway-static-keys` (key `operator_key_ids`, a comma list that begins with a comma), then roll the gateway.
   The better fix is an agent token for that client, and then take the key off the list.
2. **The operator's agent is enrolled at deploy time.** vouchryx starts with an enrolled agent, not an identity
   provider. A deploy writes the registry ConfigMap `vouchryx-agents` with one line for the operator's agent, and it
   writes the enrolment key to `agent-enrol-key` on the deploy machine (mode 0600, gitignored). Keep that file: it
   is the operator's credential for agent tokens. `agent-tokens/up.sh --registry` replaces the whole registry, so
   a file that adds an agent must also name the operator's agent.
3. **A redeploy waits for vouchryx.** The gateway and the broker fetch vouchryx's key set in an init container and
   give up after a bounded number of tries (150, two seconds apart, each with a five-second connection limit). wardryx does not start until it can read that key set. On an upgrade, vouchryx
   must be running before the gateway and wardryx are restarted, which the rollout order already does.
4. **Existing `.session-secret` on the costcrew console.** costcrew v0.10.0 refuses a session key that is not owned
   by the console's account at mode 0600. A console installed by an earlier release may hold one that is not. Run
   `chmod 600` on it once, in its data volume, before the first start of the new image. A new install creates the key
   with the right mode.
5. **The gateway's governed profile, set explicitly.** tokenfuse v1.19.0 defaults to `TOKENFUSE_PROFILE=governed`. This
   launcher sets the profile and every governed variable it depends on in `manifests/10-planes.yaml`: the budget mode,
   the firewall, the policy hook and its failmode, the declassify key, the admin keys and the client keys. So the
   profile changes nothing a deploy did not choose. The broker sets the profile too.
6. **A refused budget raise is named on the answer.** tokenfuse v1.19.0 does not let a call raise an open run's
   budget. A refused raise comes back with the header `x-fuse-budget: raise-refused; kept=<usd>`, on the 402 it
   causes as well. An agent that raised its budget mid-run must open a new run id.
7. **wardryx verifies the agent's token and proof, and the proof stays required.** The five `WARDRYX_AGENT_TOKEN_*`
   settings are set together. A proof is required, so a bearer token alone is refused. The door origins name the
   gateway and the broker as the agents address them.
8. **The printed dashboard link and the CORS origins of tokenfuse-cloud.** tokenfuse-cloud answers loopback origins
   only (`TOKENFUSE_CLOUD_CORS_ORIGINS` names others), and a dashboard key goes in the URL fragment (`#key=`). This
   launcher serves no dashboard from a non-loopback origin, so nothing here changes. An operator who serves one must
   name its origin.
9. **costcrew v0.10.0 masks prompt data, and the console needs an explicit listener choice.** The scheduled analyst
   calls keep masked prompt data (the default, unchanged here). The console's `-addr` is not loopback, so it now runs
   with `-insecure-http`. That is honest only because its Service is ClusterIP: reach it through `kubectl port-forward`
   or an encrypted tunnel, never a public address. A TLS proxy in front, with `-behind-tls`, is the better choice when
   the console is ever published.
10. **mockryx v0.3.0 owner rule for key files.** The drills' key file is `root:10001` at `0440` through `fsGroup`, which
    the rule accepts. No change.
11. **trailryx-node v1.4.0, idryx v1.3.0.** Nothing to configure. idryx's webhook header file is not used here.

## Breaking

Yes. Item 1 refuses a static key that was accepted before, and item 3 means a redeploy needs vouchryx up. Items 2 and 4
need a file kept or a mode changed by hand.

## Measured

The agent-token path, with the component pins above, was run on a local kind cluster (kindest/node 1.37.0) with
the product's images and the product's door settings. The run and what it measured are in
`evidence/require-agent-tokens-kind/`, and the rest of the stack was not run (see that folder's README).

Not working yet: the broker's second door. The broker accepted the agent token, but its tool call was refused
closed (JSON-RPC -32004), because wardryx refused the proof the broker relayed (the proof's key was not the
token's bound key). The cause is not isolated. Treat an MCP path through the broker as unverified in 1.5.0.
