# stack-k8s 1.5.0

A minor, not a patch, and breaking. The default install now requires an agent's own token at the two doors that take agent calls, the gateway and the MCP broker. A static client key is admitted only when its id is on a named list. wardryx checks the token and its DPoP proof itself. vouchryx, the service that issues the token, is in the default install and runs without an identity provider. The component pins move to the releases of 2026-10-19.

It covers everything since v1.4.0: pull request #192, one commit. The tag is a separate step, taken after the pull request is merged, so this note is written before the tag exists.

## Upgrade

Run these steps in order on a running cluster. Steps 1 to 3 change what the cluster does. Step 4 names what you must keep. Steps 5 and 6 name a file and the overlays a plain deploy does not touch.

1. **Decide which static keys stay admitted, before the deploy.** The gateway keeps five key ids admitted without a token: `felyx`, `agents`, `drills`, `costcrew` and `broker`. Each has its reason beside it in `manifests/10-planes.yaml`. Any other static key is refused after the upgrade with `401 agent_token_required`. To keep one for now, put its id in the ConfigMap `gateway-static-keys`, key `operator_key_ids`, as a comma list that begins with a comma. To have the ids on the list from the first start, create the ConfigMap before the deploy:

   ```
   kubectl -n agent-stack create configmap gateway-static-keys --from-literal=operator_key_ids=',claude-code,ci-runner'
   ```

   A deploy keeps an existing ConfigMap and never rewrites it. If you did not create it, the deploy creates an empty one, and the gateway refuses your unlisted keys until you add the ids and restart it:

   ```
   kubectl -n agent-stack patch configmap gateway-static-keys --type merge -p '{"data":{"operator_key_ids":",claude-code"}}'
   kubectl -n agent-stack rollout restart deployment/tokenfuse-gateway
   ```

   An edit replaces the whole value, so write the full list each time.

2. **Run the deploy from the 1.5.0 checkout with the flags you used before.** On a cluster that is already up, add `--skip-install` as on any re-run. The deploy (`deploy.sh`, `cloud/gcp/deploy-gcp.sh` or `cloud/aws/deploy-aws.sh`) mints what is missing and keeps what exists: the Secret `vouchryx-keys` (signing key and revoke key), the registry ConfigMap `vouchryx-agents` with one line for the operator's agent, the enrolment key file `agent-enrol-key` on the deploy machine (mode 0600, gitignored), and the static-key ConfigMap from step 1. Then it applies the manifests.

3. **Let vouchryx come up first.** The gateway and the broker fetch vouchryx's key set in an init container. It tries 150 times, two seconds apart, and each try has a five-second limit. If vouchryx does not answer in that time, the gateway or the broker pod does not start, so nothing is admitted without a token. Check `kubectl -n agent-stack rollout status deployment/vouchryx` before you read the gateway's status.

4. **Keep these, and do not delete them.** `agent-enrol-key` is the operator's agent credential for agent tokens. The deploy writes it when it creates the registry and keeps it on every later run. The Secret `vouchryx-keys` holds the key vouchryx signs with. The ConfigMap `gateway-static-keys` holds your list.

5. **Set the costcrew session key's mode once, on an upgraded console.** costcrew v0.10.0 refuses a `.session-secret` that is not owned by the console's account at mode 0600. A console installed by an earlier release may hold one that is not. Run this while the old pod is still up, before the deploy rolls the console to v0.10.0:

   ```
   kubectl -n agent-stack exec deploy/costcrew -- chmod 600 /var/lib/costcrew/.session-secret
   ```

   A new install creates the key with the right mode, so this step is for an upgraded console only.

6. **Re-apply the opt-in overlays you run.** If you run Keyryx, run `keyryx/up.sh` again: its `wardryx-patch.yaml` moves wardryx to v2.3.0, and a wardryx older than v2.3.0 does not check agent tokens. If you turned agent tokens on in 1.4.0 with `agent-tokens/up.sh`, the switch is now the default. See Breaking for what was removed and the way back.

## Breaking

Yes. Each breaking change, with its migration:

- **A static key that is not on the list is refused.** The gateway answers `401 agent_token_required` to a static key whose id is not on its list, and the answer does not name the list. Migration: step 1 of Upgrade. Then move the client to an agent token. Enrol an agent with `./agent-tokens/up.sh --registry agents.txt --check-only`, then without `--check-only`. The file replaces the whole registry, so it must name the operator's agent too, as `agent://<trust domain>/agents/operator|agents|stack|sha256:<digest>`, where the digest is of the key in `agent-enrol-key`. An agent pod gets its token from a projected service-account token, as `agent-tokens/example-agent.yaml` shows. Once the client holds a token, take its id off the list.

- **The 1.4.0 opt-in is no longer a switch.** `agent-tokens/down.sh` and the patch files `manifests/58-agent-tokens-*-patch.yaml` and `*-unpatch.yaml` are removed. `agent-tokens/up.sh` now writes the registry and switches nothing. Migration: none for a cluster that runs the 1.5.0 manifests. To go back to the 1.4.0 posture, where static keys work as before this release and an agent token works beside them, set the value on both doors by hand:

  ```
  kubectl -n agent-stack set env deployment/tokenfuse-gateway TOKENFUSE_AGENT_TOKENS=accept
  kubectl -n agent-stack set env deployment/tokenfuse-mcp-broker TOKENFUSE_AGENT_TOKENS=accept
  ```

  The next apply of these manifests sets `require` again, so the way back lasts only until then. Nothing in this release runs that path on a cluster.

- **A refused budget raise.** tokenfuse v1.19.0 does not let a call raise an open run's budget. A refused raise is reported on the answer, including the 402 it causes, as `x-fuse-budget: raise-refused; kept=<usd>`. Migration: an agent that needs more budget in the middle of a run opens a new run id.

- **A redeploy needs vouchryx up.** Migration: step 3 of Upgrade.

- **A costcrew session key with the wrong mode is refused.** Migration: step 5 of Upgrade, once, before the new console starts.

## Changes, by area

- **Agent tokens at the doors (invariant 54).** The gateway (`manifests/10-planes.yaml`) and the MCP broker (`manifests/52-tokenfuse-mcp-broker.yaml`) run `TOKENFUSE_AGENT_TOKENS=require` under `TOKENFUSE_PROFILE=governed`. The profile is set explicitly, so it changes nothing a deploy did not choose. Both fetch vouchryx's key set at start. The audience is one https identifier, `https://vouchryx.agent-stack.invalid`, and vouchryx, the gateway, the broker and wardryx all name that same value. The revocation list fails closed and is at most 60 s old. The NetworkPolicy `gateway-ingress-mcp-broker` in `manifests/58-agent-tokens-network.yaml` admits the MCP broker to the gateway on TCP 4100 and nothing else, so the broker's tool-call check does not depend on the planes policy. Gate: `scripts/agent-tokens-are-required.sh`.

- **Static keys named (invariant 62).** The stack's own list is written in `manifests/10-planes.yaml`, with a reason beside each id. The operator's additions come from the ConfigMap `gateway-static-keys`. That ConfigMap is created empty by `lib/static-keys.sh`, is in no manifest, and is never rewritten by a deploy. The broker's list is `broker-caller` only. Gate: `scripts/static-keys-are-named.sh`.

- **vouchryx in the default install, agents-only (invariant 24, amended).** vouchryx runs with no identity provider. The deploy mints its signing key and revoke key and enrols the operator's agent (`lib/vouchryx-mint.sh`). Trusting an identity provider stays opt-in: `delegation/up.sh` refuses to run unless it is given an issuer, an audience and a JWKS file. Gate: `scripts/vouchryx-runs-agents-only.sh`.

- **wardryx verifies the token itself (invariant 63).** wardryx v2.3.0 checks the agent token's signature against vouchryx's key set and checks its revocation status. It checks the DPoP proof against the key the token is bound to, the proof's `ath` (the hash of the token), its `htu` (one of the door origins, the gateway and the broker as agents address them) and its `iat`, which must fall within `WARDRYX_AGENT_TOKEN_PROOF_MAX_AGE_SECONDS` (1 to 300) of now. The proof is required, so a bearer token alone is refused. The five `WARDRYX_AGENT_TOKEN_*` settings are set together, and a partial set refuses to start. An asserted agent that the token does not name is answered 403. Gate: `scripts/wardryx-verifies-agent-tokens.sh`.

- **Retired with the opt-in.** The gates `agent-tokens-are-wired.sh` and `delegation-off-by-default.sh` are removed, with the opt-in they checked.

- **costcrew v0.10.0.** The scheduled analyst calls keep masked prompt data, which is the default and unchanged here. The console listens on a non-loopback address, so it now starts with `-insecure-http`. That is honest only because its Service is ClusterIP. Reach the console with `kubectl port-forward` or an encrypted tunnel, never a public address. Put a TLS proxy in front, with `-behind-tls`, before the console is ever published.

- **mockryx v0.3.0.** Its key file check follows PostgreSQL's rule, under which a root-owned file may be group-readable. The drills' key file, `root:10001` at 0440 through `fsGroup`, passes. No action.

- **Records.** Invariants 24, 54, 62 and 63 in CLAUDE.md, each with its gate. Teeth cases for the four new gates in `scripts/gates-have-teeth.sh`. Gotchas 142 to 144 hold the traps behind this release.

## Measured

Run on a local kind cluster with the 1.5.0 pins and the product images at their digests: `evidence/require-agent-tokens-kind/run-v1.19.0.sh`, output in `output-v1.19.0.txt`, exit 0, every check as expected. The provider and the MCP upstream are stand-ins. The gateway, the broker and wardryx run the product images.

- vouchryx: the enrolled operator agent gets a token for the one audience (200). Another audience is refused (400). A wrong enrolment secret is refused (401).
- Gateway: a token and its proof (200). A stranger's proof, no proof, and a token beside a static key are each refused (401). A header naming another agent is refused (403). A listed static key is admitted (200). An unlisted static key is refused (401, `agent_token_required`).
- Broker: a token and its proof reach the MCP stub (200, `stub answered lookup`). A stranger's proof is refused (401).
- wardryx: the agent's own token and proof are admitted (200). An asserted agent that the token contradicts is refused (403). A proof from another key is refused (403).

The earlier run, before the broker's network rule, is kept as `output-v1.19.0-before-broker-door.txt`. There the broker's tool call was refused closed with `-32004` ("the taint gate could not be reached"): the broker could not reach the gateway's tool-call check. The NetworkPolicy rule in this release is the fix, and the run after it passes.
