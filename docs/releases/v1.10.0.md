# stack-k8s 1.10.0

A minor release with one breaking change. Every plane that writes the events bus runs under a uid and a group of its own, and only the bus owner can create, rename or remove a name in the bus directory, so no plane can forge or replace another's stream (estate-gates GAPS G3.16). The scheduled drills can start again and see what they wait for, and a drill of its own beside heraldyx proves the whole reaction chain to the operator's mail (G3.20). The Go builds move to Go 1.27.4, the installers check what they download, and a deploy whose proof failed ends red.

## Upgrade first

1. **Breaking: the bus layout changes on a running cluster (#239, CLAUDE.md invariant 89).** Every writing plane's uid changes, and the streams move from the root of the `stack-events` claim into `streams/`. The new Job `bus-owner` (uid 20000) copies each stream of the old layout into `streams/` once, with wardryx's policy archive and the chain verifier's memory, so the hash chains continue. The old files stay where they are and nothing reads them after the change. The planes' own state claims keep their `fsGroup`, so a file an earlier uid wrote stays writable to the new one through the group.

   Lines a plane writes between the copy and its own restart land in the old file and are not copied, so stop the writers first, apply, and let the owner run before they start again:

   ```sh
   kubectl -n agent-stack scale deploy --all --replicas=0
   kubectl -n agent-stack delete job bus-owner --ignore-not-found
   kubectl apply -k manifests/
   kubectl -n agent-stack wait --for=condition=complete job/bus-owner --timeout=300s
   ```

   `kubectl apply -k` puts every Deployment back at its declared replicas, and each plane's `bus-ready` init waits for the owner's marker before it starts. A cluster you would rather start clean needs only a new `stack-events` claim: the owner makes every stream empty. The new uids: wardryx 20001, vouchryx 20002, typryx 20005, gateway 20010, MCP broker 20012, control plane 20013, verdryx-slo 20020, console 20030, drills 20040, chain verifier 10002, costcrew 10003.

   Going back to 1.9.0 puts every plane back on the files at the claim's root, as they were when the owner copied them; what was written under `streams/` since is not read by 1.9.0.
2. **Re-run the launcher, or apply the manifests of this tag.** Images move by tag and digest:

   | Image | 1.9.0 | 1.10.0 |
   |---|---|---|
   | mockryx (`drills`, `drills-broker`, and the new `drills-heraldyx`) | v0.5.0 `32e4e79c` | v0.5.1 `39265122` |

   This tag also publishes the console image, `genaryx-console:v1.10.0`, built with mockryx v0.5.1 (the 1.9.0 tag built it with v0.4.0) and with its Go tools on Go 1.27.4, and the two tunnel images, `stack-caddy` and `stack-wg`, on Go 1.27.4. The manifests of this tag pin the console image they pinned before, `genaryx-console:v1.8.8`.
3. **A deploy whose proof failed ends red (#238, invariant 88).** `deploy.sh`, `deploy-aws.sh` and `deploy-gcp.sh` kept `|| true` after `verify.sh` and `security-tests.sh`, printed "Done." and exited 0. They now keep both exit codes, still print the way in, name the failed check in place of "Done." and exit 1. A pipeline that ran a deploy and read only its exit code now sees a failed proof.
4. **The installers check what they download (#238, invariant 87).** Longhorn v1.7.2, Calico's tigera-operator v3.29.1, Hetzner's cloud controller manager v1.21.0 and the k3s v1.36.2+k3s1 install script, taken from its tag rather than `get.k3s.io`, are fetched once on the operator's machine through `lib/verified-fetch.sh`, compared with a sha256 pinned per version and applied over stdin. A download whose hash differs stops the install; moving one of those versions needs a new row in that library.
5. **The scheduled drills (#240, #241, invariant 90).** `drills` watches the three bus streams its scenarios wait on (`tokenfuse.ndjson`, `wardryx.ndjson`, `verdryx.ndjson`) and has `backoffLimit: 0`, so a drill that finds a gap does not run its hostile scenarios again. Its set replaces the image's `reaction-chain-reaches-heraldyx.yaml` with this cluster's copy that stops at wardryx's record, because heraldyx's journal is on heraldyx's own volume; mockryx v0.5.1 also ships that check as `reaction-chain-reaches-wardryx`, so a run checks wardryx's record twice, under two names. The new `drills-heraldyx` ships suspended in `45-heraldyx.yaml`: it runs on heraldyx's node, reads heraldyx's journal read only, and waits for heraldyx's `alert_sent` for its own denied request. **Each run sends the operator one real mail**, and inside `HERALDYX_QUIET` hours it is a Finding about the hour. Run it with:

   ```sh
   kubectl -n agent-stack create job --from=cronjob/drills-heraldyx drills-heraldyx-now
   kubectl -n agent-stack logs -f job/drills-heraldyx-now
   ```

## What changed

- **One uid and one group per bus writer** (#239, invariant 89, GOTCHAS 164). `manifests/11-bus.yaml` adds the Job `bus-owner`, the only pod that mounts the claim's root read-write: `streams/` is `20000:10001 2750`, each stream `20000:<producer gid> 0664`, and a producer appends through its group. Every pod mounts `streams/` by subPath at `/var/lib/stack/events` (paths unchanged) behind a `bus-ready` init. `security-tests.sh` 11c: a pod in costcrew's identity, bus mounted read-write, is refused on `wardryx.ndjson` and on any rename or new name.
- **Go 1.27.4** (#238, invariant 86): the five Dockerfiles that build Go (`go-service`, `caddy`, `wg`, `console`, `scopyx-browser`) build on `golang:1.27.4-alpine`, pinned by index digest, for GO-2026-6859.
- **No tracked binary** (#238): a committed Mach-O arm64 build of `images/uapi-proxy` is removed, and `scripts/no-binary-is-tracked.sh` refuses an ELF, Mach-O or PE file in the tree.
- **The drills can start** (#240, invariant 90): mockryx v0.5.0 refuses to start when a scenario waits for a reaction and no log is named, so `drills` failed on every run on main. `scripts/drills-can-start.sh` reads every mockryx CronJob's scenario set as its pod sees it.
- **The heraldyx drill** (#241, GAPS G3.20): see Upgrade, item 5.
- **mockryx v0.5.1** (#242): the reaction chain and the game-day drills wait for heraldyx in the step heraldyx reacts to, which removes a false Finding on a healthy stack; built with Go 1.27.4. The console image of this tag carries it (#237, #242).

## Measured

- The bus layout on k3s v1.36.2+k3s1 with Longhorn v1.7.2 in a guest on forge (`evidence/bus-per-producer-longhorn/`): in the old shape a pod as costcrew appended a forged `policy_allow` to `wardryx.ndjson` and a pod as typryx replaced the gateway's stream; in the new shape every one of those is refused, also on `local-path`. `deploy.sh --skip-install --skip-images` from the branch, three runs over one cluster: the third ends green, `verify.sh` 24 passed, `security-tests.sh` 29 passed, 11c included.
- The download hashes measured with `curl -fsSL <url> | sha256sum` on two machines, identical; `get.k3s.io` served a different script the same day. Every new gate red first on the tree before it: `no-binary-is-tracked.sh`, `remote-fetches-are-verified.sh` (31 problems), `deploy-ends-red-when-its-proof-fails.sh` (18), `bus-writers-are-separate.sh` (60), `drills-can-start.sh` (five problems on `31410ef`, four on `0e80406`).

With no network and no gateway it loads `drills`' fourteen scenarios with this cluster's copy mounted and the CronJob's watch list, loads each ConfigMap copy, and refuses the heraldyx copy with no watch list (exit 2), on forge, 2026-11-12.
