# stack-k8s 1.1.48

This release re-publishes the three images this repository builds, `genaryx-console`, `stack-caddy` and
`stack-wg`, with their image signatures written in the legacy format (#185). The workflows are otherwise
unchanged. Merging this release changes no running cluster on its own: the manifests still name v1.1.47 and
the upstream digests, and the pins to v1.1.48 come in a separate pull request after the tag, as the
console pins did for v1.1.45 and v1.1.46.

## What the tag builds

Pushing the tag `v1.1.48` starts two workflows and nothing else:

- `console-image.yml` publishes `ghcr.io/taipanbox/genaryx-console:v1.1.48`, built for amd64 and arm64 from
  the tag's `images/console.Dockerfile`. Its five source repositories are checked out at their default-branch
  head at build time, and the image's labels record the commits it was built from.
- `tunnel-images.yml` publishes `ghcr.io/taipanbox/stack-caddy:v1.1.48` and `ghcr.io/taipanbox/stack-wg:v1.1.48`.

No other image is built by this repository.

## What changes, and what does not

- Both image workflows sign each image by digest with cosign v3.1.3 and the two flags
  `--new-bundle-format=false --use-signing-config=false`. The signature is written as a `.sig` tag, the form
  the admission policy in `policy/` reads (policy-controller v0.15.1 reads no other form). The signing identity
  is unchanged: the workflow at the tag, keyless. The provenance attestation is unchanged.
- The admission policy is opt-in and unchanged. Once the v1.1.48 images carry a `.sig` tag the policy can admit
  them. It stays off for a running stack until the pins move and an operator opts in.
- The two flags are deprecated in cosign v3. The comment next to each sign line says when to remove them: when
  policy-controller reads the bundle format for image signatures (upstream PR sigstore/policy-controller#1968).

## What an existing cluster does

Nothing, on merge or on a re-apply: the manifests still name v1.1.47 and the upstream digests.

## Not measured before the tag

- A keyless signature with these two flags, on a real tag. A key-signed test with the same flags was admitted by
  the policy on kind; the keyless path accepts the flags up to the OIDC step. The tag run is the first real one.
