# stack-k8s 1.1.11

The planes that can move now leave a dead node in about a minute and a
half instead of six, and a rolling update of them stops dropping requests.
The typed-answer plane arrives as an opt-in.

## What changed

- **A node loss no longer costs five minutes (#102).** Every Deployment is
  one replica, and Kubernetes waits 300 s by default before evicting a pod
  from a node that has died. `tokenfuse-gateway`, `wardryx` and `idryx`, the
  three Deployments that roll and hold no ReadWriteOnce claim, now tolerate
  an unreachable or not-ready node for 30 s. `tokenfuse-cloud` and the
  console keep the default: their volume cannot follow them faster.
- **A rolling update drains first (#102).** The serving container of each of
  those three sleeps 5 s before it stops, so its endpoint leaves the Service
  while it still answers. A new gate, `scripts/planes-leave-a-dead-node.sh`
  (invariant 21), fails if either setting is lost.
- **typryx, the typed-answer plane, as an opt-in (#98, #101).**
  `manifests/51-typryx.yaml` and `52-tokenfuse-mcp-broker.yaml`, applied
  only with `--with-typed`, never by the default `apply -k`. Its journal is
  on the shared bus and tokenfuse's MCP broker fronts it by configuration.

## Measured

On a three-node k3d cluster on one 4-core box (k3s v1.36.2 with the
installer's server flags, Calico v3.29.1), a probe hitting every plane's
health endpoint four times a second:

| | Before | After |
|---|---|---|
| node running the gateway killed | gateway down 360 s | 88.5 s |
| node running idryx killed | idryx down 347 s | 83 s |
| gateway rolling restart | 3 requests refused in 0.8 s | 0 of 348, three restarts |

The same cluster ran 1.1.7 and upgraded to 1.1.10 live, which the 1.1.10
notes said had not been done: verify.sh 16 passed, 0 failed, and
security-tests.sh 24 passed, 0 failed, on both, and again on this release.

## Upgrade

`kubectl apply -k manifests`. The gateway, wardryx and idryx restart once.

## Not in this release, said plainly

- The cluster ran in containers. Longhorn cannot run there, so the shared
  volume was one host directory mounted into every node: it showed sharing
  across nodes and the ownership the stack relies on, not replication or
  how fast a Longhorn volume detaches from a dead node.
- One replica still means an outage while a new pod starts. This shortens
  the wait for it; it does not add a replica.
- typryx and the broker were not applied on that cluster; they were proven
  on kind the day they merged.
