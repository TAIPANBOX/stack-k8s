# stack-k8s 1.6.1

A minor on the 1.6 line. It completes what 1.6.0 staged: the record seal pins its Keyryx key, the witness's attestations reach the record seal, the approver statements are checked, and the console and Keyryx are pinned to the releases that carry them. It also stops the cloud launchers from moving Felyx off its configured model.

## Upgrade

1. **The record seal pins its Keyryx key.** trailryx-node 1.5.0 refuses to start without `TRAILRYX_KEYRYX_KID`. The launcher reads custody's one ES384 key for `trailryx-root` once custody is up, and writes its kid into the `stack-wiring` ConfigMap. A key set with no ES384 key, or with more than one on a first install, stops the install and says why. A re-run keeps the pin. To rotate on purpose, custody publishes a successor ES384 key and you re-run the launcher with `KEYRYX_ROTATE_KID=<kid of the successor>`. The pin moves to that kid and nothing else changes. The kid is public, and no key value is printed (invariant 73).
2. **`trailryx-root` is an ES384 key.** The custody policy changes it from ES256, which the record seal cannot use. An existing install gets the ES384 key on its next run, and the pin follows it. Until the pin is written, the seal refuses to start, which is loud rather than silent.
3. **The witness runs as group 10001**, the record plane's group, so the record seal can read the attestations it writes, read only, through `TRAILRYX_WITNESS_ATTESTATIONS` (invariant 70). Attestation files that keyryx 0.1.1 wrote keep mode 0600. keyryx's 0.1.2 notes give the one-time `chmod` for them, which the witness's account must run (GOTCHAS 152).
4. **Keyryx v0.1.2 and trailryx-node v1.5.0 are pinned by tag and digest** (invariant 72).
5. **The console is pinned to `genaryx-console:v1.6.0` by digest,** in the console and in the quality-drift CronJob. With that image, wardryx checks each approver statement: `WARDRYX_APPROVER_JWKS` is set, and the JWK set is mounted read only from `wardryx-approver-jwks`. A console older than v1.6.0 sends no statement, so do not pin an older console with this release (invariant 67).
6. **Felyx keeps its configured model.** `--anthropic-key-file` gives the gateway its provider key and no longer switches the copilot to `claude-sonnet-5`. To move Felyx to that model, apply `manifests/55-copilot-cloud.yaml` by hand: it is metered on that key's account (GOTCHAS 154).
7. **tokenfuse is pinned at v1.20.0 by digest**: the gateway, the MCP broker, the `focus-export` sidecar and the control plane. The gateway's `TOKENFUSE_DELEGATION_ORIGINS` names its Service name and its cluster-internal name; the broker's `TOKENFUSE_DELEGATION_ORIGINS` and `TOKENFUSE_MCP_PROOF_ORIGINS` name its two names. A delegation or MCP proof addressed to one of them is accepted, and one addressed anywhere else is refused (invariant 74). The MCP proof door stays off until an operator configures clients for it.


## Not in this release

- The tokenfuse-dashboard image: it has a v1.20.0 tag, and no manifest runs it, so this release pins nothing for it.

## Not measured

- Keyryx v0.1.2 and trailryx-node v1.5.0 on a live cluster: the ES384 key an existing custody publishes, the first pinned pack, and the witness's attestation files and their group.
- Approver statements end to end: a console statement through a live gateway, granted or refused.
- The tokenfuse v1.20.0 gateway and broker, started with their origin lists, were not run against a cluster: the gateway was started in Docker with its origin variables and served its listener past the origin check; the broker gate ran the broker with its own switches.
- Every gate in this release runs on static text and stub binaries. None of them ran a cluster.
