# stack-k8s 1.1.30

Pins only: costcrew moves to `v0.4.0`.

## What moves

- **costcrew `v0.3.0` -> `v0.4.0`** (opt-in, `manifests/49-costcrew.yaml`): the
  `costcrew` console Deployment and the `costcrew-crew` CronJob, one image for
  both. The tag is costcrew `eeee11e`, published 2026-10-08 for amd64 and arm64
  (index `sha256:bd52fdaab81781fcdad2db259f26fc1164e1be50acc92ffc29a1e75fea93afbb`,
  read with `docker buildx imagetools inspect`). This launcher pins by tag.
  Release notes:
  [costcrew v0.4.0](https://github.com/TAIPANBOX/costcrew/releases/tag/v0.4.0).

No other pin moves. Every flag this manifest passes (`-addr`, `-data`,
`-stack-events`, `-stack-passports`, `-stack-host`, `-stack-owner` on the
console; `-due`, `-data`, `-live`, `-ceiling`, `-stack-events`, `-stack-host`
on the runner) still exists at the tag, the runner still reads
`OPENROUTER_API_KEY` and `ANTHROPIC_API_KEY`, and the image still runs as
65532:65532 with the console as its entrypoint and `costcrew-run` at
`/usr/local/bin/costcrew-run`.

## Upgrading

- **Everybody signs in to the costcrew console again once.** Session tokens
  are now stored hashed. Old sessions are ended at the first start of v0.4.0
  and journaled as `sessions_reset`. Accounts are untouched.
- **The console's files become private.** At start it sets `app.db`, its
  `-wal` and `-shm`, and the journal to 0600. It would create a missing data
  directory 0700, but here `/var/lib/costcrew` is the mount root of
  `costcrew-state`, which already exists, so it keeps its mode. This fits
  the manifest:
  - Both pods that mount `costcrew-state` (the console and the
    `costcrew-crew` runner) run as `65532:65532`, so the runner still owns
    and opens the same 0600 files. No other workload mounts the claim.
  - Each time a pod mounts the claim, the kubelet's `fsGroup: 65532` pass may
    add group read-write back to those files. The console and the runner both
    open the store through the same code, which sets them to 0600 again. Group
    65532 is the same account, so this widens nothing.
  - `costcrew.ndjson` on `stack-events` and the passport files stay readable
    by the other services, as in v0.3.0.
- **Request bodies over 1 MiB get 413.** Nothing in this stack sends the
  console a request: only a person's browser does. The intake upload keeps
  its own larger cap.
- **With a gateway configured, an analyst with no owner is refused.** This
  manifest configures no gateway for costcrew (no `-gateway` and no
  `COSTCREW_GATEWAY`), so this changes nothing here.
- **A fifth binary.** The image now also carries `costcrew-usage`, next to
  `costcrew`, `costcrew-run`, `costcrew-enforce` and `costcrew-idryxsource`.
  This launcher runs the first two and starts none of the others.
- **New optional flags, none set here.** On the console: `-oidc-*`,
  `-prompt-data`, `-typryx-url`. On the runner: `-model-url`, `-model-name`,
  `-max-run-tokens`, `-prompt-data`. With none set the console behaves as
  v0.3.0 apart from the notes above.

## Not proven

- **This exact set on a cluster.** v0.4.0 has not been deployed from these
  manifests, and `verify.sh` and `security-tests.sh` were not run against it.
- **The permission sequence above.** It is read from costcrew's code and from
  how the kubelet applies `fsGroup`, not watched on a pod.
- **The sign-in reset on this stack.** It is costcrew's own measured
  behaviour, not exercised here.
