# stack-k8s 1.1.44

TokenFuse moves from `v1.11.0` to `v1.13.0` in one pin. That crosses three TokenFuse
releases: `v1.11.1` (a mistyped firewall mode refuses to start), `v1.12.0` (an agent's
memory is judged as untrusted context, and nine security switches refuse a mistyped
value at start) and `v1.13.0` (the price book of 2026-10-13, with prompt-length tiers).
This launcher writes only words TokenFuse accepts, so every pod starts with the new pin.

The same release moves three more pins that the TokenFuse notes do not cover: wardryx
`v1.3.0` -> `v1.3.2`, genaryx-console `v1.1.36` -> `v1.1.43`, and scopyx `v1.0.0` -> `v1.0.1`
(with its chromium variant, `v1.0.0-chromium` -> `v1.0.1-chromium`). Each is set out below,
with what it changes for a deployment.

## Upgrading

- **Nothing to configure.** No environment name is renamed, removed or added by `v1.12.0`
  or `v1.13.0`, so the manifests change only at the pins.
- **Can a value this launcher writes be refused? No.** Every value in the table above is an
  accepted word. An operator value passed through `--pii-mode` or `--firewall` is checked by
  `pii/mode.sh` or `firewall/mode.sh` before anything is installed, and both accept exactly the
  words TokenFuse accepts. A misspelt value stops the deploy script, not the pod.
- **Enforce now judges memory (`v1.12.0`).** The starter policy labels the output of Engram's
  `recall` and `why` as `memory`, and `no-exec-after-untrusted` now lists it. This launcher runs
  the firewall in enforce, so a run that has read memory cannot then run an exec, write or
  network-egress tool. That is TokenFuse's intended behaviour, not measured on a cluster.
- **Unclassified tools are named once in the gateway log (`v1.12.0`).** A log line only, with no
  change to any decision.
- **Listed models are charged at their vendor rates (`v1.13.0`).** Claude Haiku 5.5 and the other
  newly listed ids leave the 15 / 75 fallback. A budget sized against fallback-priced calls admits
  more of them. This launcher sets no `TOKENFUSE_PRICE_BOOK`, so the built-in book applies.

## What the other moves change

### wardryx 1.3.1 and 1.3.2

- **What loads that did not load before: nothing from this launcher.** Wardryx 1.3.1 loads every
  document of a multi-document policy file, where before only the first was read. The
  `wardryx-policy` ConfigMap in `manifests/00-base.yaml` holds one YAML document: one `policy.yaml`
  key with a single list of three policies. So the same three policies load as before, and no
  file here holds a second document that was being dropped.
- **What is refused now.** From 1.3.2, a PUT to `/v1/policies/{id}` with a key the policy does not
  declare gets a 400, and nothing is stored (before, the key was dropped and the write answered 200).
  Nothing in this repository sends such a PUT: the README example sends only declared keys,
  `security-tests.sh` and `verify.sh` read or delete policies, and a grep of the genaryx console
  source finds no PUT to `/v1/policies` (2026-10-13). Anyone who writes policies by hand should check
  the keys they send.

### genaryx-console 1.1.36 -> 1.1.43

The image is built from this repository's tag, and its labels record the commit of each component it
bundles (`dev.taipanbox.source.*`, read from the registry config on 2026-10-13):

| Component | v1.1.36 | v1.1.43 | Commits in the range, local clone |
|---|---|---|---|
| genaryx | `41972c6` | `4fc39b3` | 1: `docs(claude): invariant 22 ... (#107)`, which changes CLAUDE.md only |
| engram | `82c3954` | `6d43312` | 1: `feat: record and return where each memory came from (provenance) (#58)` |
| mockryx | `3d099cb` | `7fa6dd5` | 4 (#65 to #68): token-flood and pii-in-prompt drills, tool history with `--mcp-broker`, the declared-tool-poisoning drill, the allow-list renamed-tool drill |
| qryx, verdryx | `fcc9910`, `bef9589` | the same | none |

- **Genaryx's own code is unchanged** between the two images. The one commit in its range changes
  CLAUDE.md only. The sign-in and operator behaviour of `v1.1.36` (the v1.1.37 notes) stays.
- **Engram adds a column when an existing store is opened.** The provenance change adds one nullable
  column, `episodes.provenance`, through `migrate()`, with no default and no existing row rewritten.
  Recall, `why`, the MCP tools, the adapters and export and import carry the provenance. The commit
  says ranking is unchanged and that an older Engram opens such a store and reads it unchanged. Not
  run here against a store from this launcher.
- **The console's mockryx is not the release the drills run.** The console bundles mockryx at
  `7fa6dd5`, which `git describe` places 57 commits after the `v0.2.1` release. The `drills` CronJob
  (`manifests/40-routines-and-secrets.yaml`, 416) keeps its own pin, `mockryx:v0.2.1`, and does not
  move, so the new drills run only from the console's copy.

### scopyx 1.0.1

- One fix, on the chromium backend: each subresource a page loads is now decided against the policy
  plane (wardryx, in this launcher) through the fetch's own memo. A subresource the policy refuses
  renders without that subresource, and the record counts it as blocked. A rendered page costs one
  `/v1/decide` per distinct subresource host it names.
- The external (non-browser) backend is unchanged. Nothing frozen in `compat/1.0.json` moves.
- scopyx is opt-in here (`47-scopyx.yaml` and `48-scopyx-browser.yaml`), so this changes a deployment
  only where it is applied. Not run: a chromium fetch through this launcher.
