# stack-k8s 1.1.44

TokenFuse moves from `v1.11.0` to `v1.13.1` in one pin. That crosses four TokenFuse
releases: `v1.11.1` (a mistyped firewall mode refuses to start), `v1.12.0` (an agent's
memory is judged as untrusted context, and nine security switches refuse a mistyped
value at start), `v1.13.0` (the price book of 2026-10-13, with prompt-length tiers) and
`v1.13.1` (the MCP broker caps tool-call arguments at the policy plane's bound, and the
datafusion dependency moves). This launcher writes only words TokenFuse accepts, so every
pod starts with the new pin.

The same release moves four more pins that the TokenFuse notes do not cover: wardryx
`v1.3.0` -> `v1.3.2`, genaryx-console `v1.1.36` -> `v1.1.43`, and scopyx `v1.0.0` -> `v1.0.1`
(with its chromium variant, `v1.0.0-chromium` -> `v1.0.1-chromium`), and costcrew `v0.5.0` -> `v0.6.0`.
heraldyx `v0.4.0` -> `v0.5.0` and idryx `v1.1.0` -> `v1.2.0` move too. Each is set out below,
with what it changes for a deployment. The release also adds the identity files feature
(#157, opt-in, invariant 39).

## Upgrading

- **Nothing to configure.** No environment name is renamed, removed or added by `v1.12.0`,
  `v1.13.0` or `v1.13.1`, so the manifests change only at the pins. heraldyx, idryx and the
  identity files need no configuration either (see their sections above).
- **Can a value this launcher writes be refused? No.** Every value in the table above is an
  accepted word. An operator value passed through `--pii-mode` or `--firewall` is checked by
  `pii/mode.sh` or `firewall/mode.sh` before anything is installed, and both accept exactly the
  words TokenFuse accepts. A misspelt value stops the deploy script, not the pod.
- **Enforce now judges memory (`v1.12.0`).** The starter policy labels the output of Engram's
  `recall` and `why` as `memory`, and `no-exec-after-untrusted` now lists it. This launcher runs
  the firewall in enforce, so a run that has read memory cannot then run an exec, write or
  network-egress tool. That is TokenFuse's intended behaviour, not measured on a cluster.
- **Unclassified tools are named once in the gateway log (`v1.12.0`).** A log line only, with no
  change to any decision.
- **Listed models are charged at their vendor rates (`v1.13.0`).** Claude Haiku 5.5 and the other
  newly listed ids leave the 15 / 75 fallback. A budget sized against fallback-priced calls admits
  more of them. This launcher sets no `TOKENFUSE_PRICE_BOOK`, so the built-in book applies.

## What the other moves change

### tokenfuse 1.13.1

The TokenFuse `v1.13.1` notes (`docs/releases/v1.13.1.md` at the tag) name two changes, and the
commits between the tags agree with them (`git log --no-merges v1.13.0..v1.13.1`, 2026-10-13).

- **MCP broker: tool-call arguments capped at 12 KiB (`dd9ea7e`).** The broker used to send a call's
  arguments to wardryx whenever they fit 16 KiB, and wardryx refuses arguments over 12 KiB, so a call
  of 12 to 16 KiB got no verdict and the failmode decided it. Over 12 KiB the arguments are now dropped
  and flagged `arguments_truncated: true`, which wardryx accepts and decides on. The failmode is
  unchanged. Here this reaches only `tokenfuse-mcp-broker`, which is applied with `--with-typed`.
- **Dependencies: datafusion 44 to 55, parquet 53 and thrift dropped (`6c1fa61`).** The commit says the
  trace store, the SQL query, the FOCUS export that the `focus-export` sidecar runs, the backtest, and the
  keys and outcome reports compile unchanged and keep their test expectations. The workspace Rust version
  moves from 1.90 to 1.94. See "Not proven" for what that means for a source build.
- **Documentation only** (`ad97853`, `fba8b02`, `9b82028`, `391436d`), and a bump of a recipe dependency
  (`867c710`, pydantic-ai-slim) that is not in the gateway or the cloud binary.
- No environment name is added or removed in that range (checked by comparing the `TOKENFUSE_` names
  in the added and removed lines of the `*.rs`, `*.toml`, `*.sh` and `*.yaml` diff).

### Identity files (#157, opt-in, invariant 39)

The cluster launcher takes the gateway's client keys and identity map as files, as stack-single does.

- **`identity/up.sh`** is an opt-in script, not a manifest and not a deploy flag. It reads the keys file and
  the map file, runs the pinned gateway image's own check against them in a throwaway container (no network,
  read-only root, uid 10001), and only then writes the Secret `gateway-client-keys` (from stdin, never on an
  argument line) and the ConfigMap `gateway-identity-map`. A re-run keeps both.
- **`manifests/10-planes.yaml`** gains the gateway's env and volume blocks only: `TOKENFUSE_CLIENT_KEYS` and
  `TOKENFUSE_IDENTITY_MAP` from optional references, and the identity map mounted read only at
  `/etc/tokenfuse/identity`. A cluster that names no file starts exactly as before. No image line changes.
- **The gateway rolls when what it reads changes**: `up.sh` writes the map's sha256 and the Secret's
  resourceVersion onto the pod template, because a ConfigMap change restarts nothing by itself.
- **Gate**: `scripts/identity-files-are-checked.sh` (in `gates.yml`), 36 teeth cases, and the feature
  `features/client-keys-and-the-identity-map.feature`.
- **Evidence in the PR**: `evidence/identity-kind/run.sh` on kind v0.33.0 with Kubernetes v1.37.0 and
  tokenfuse v1.11.0, 46 of 46 checks, twice from an empty cluster (`evidence/identity-verified.md`).
  That run predates the v1.13.1 pin.

### wardryx 1.3.1 and 1.3.2

- **What loads that did not load before: nothing from this launcher.** Wardryx 1.3.1 loads every
  document of a multi-document policy file, where before only the first was read. The
  `wardryx-policy` ConfigMap in `manifests/00-base.yaml` holds one YAML document: one `policy.yaml`
  key with a single list of three policies. So the same three policies load as before, and no
  file here holds a second document that was being dropped.
- **What is refused now.** From 1.3.2, a PUT to `/v1/policies/{id}` with a key the policy does not
  declare gets a 400, and nothing is stored (before, the key was dropped and the write answered 200).
  Nothing in this repository sends such a PUT: the README example sends only declared keys,
  `security-tests.sh` and `verify.sh` read or delete policies, and a grep of the genaryx console
  source finds no PUT to `/v1/policies` (2026-10-13). Anyone who writes policies by hand should check
  the keys they send.

- One fix, on the chromium backend: each subresource a page loads is now decided against the policy

### costcrew 0.5.0 -> 0.6.0

The notes are costcrew's own `docs/releases/v0.6.0.md` (costcrew #121 to #127). What changes for a deployment:

- **Two nullable columns on `drivers`, added at start.** `expected_daily_cents` and `team`. Rows written
  before this release read NULL and behave as before, and no data is rewritten. The table is in the
  store on the `costcrew-state` claim (`manifests/49-costcrew.yaml`), so the first start of the new image
  on an existing claim adds the columns.
- **A new decision class, `driver.announced`.** It names a service, a window, the expected change of the
  service's daily cost (negative for a saving) and optionally one team. The optimizer, optimizer-onprem,
  ai-spend-analyst and forecaster roles may propose it, and only the owner's answer applies it. The
  detector judges a day inside an announced window against the announced step, so a saving that lands as
  announced is not raised as an anomaly. One that lands short, late or in the wrong direction is raised,
  with the decision's name on it. The decision request shows it to the owner like any other option.
  Nothing to configure: the roles are built into the binary.
- **Anthropic list rates in the price table.** Claude Sonnet 5 moves from 3.00 / 15.00 to 2.00 / 10.00
  per million tokens, and Claude Opus 5 from 15.00 / 75.00 to 5.00 / 25.00. The notes give Anthropic's
  pricing page, read 2026-10-13, as the source; both rows were marked unverified before. The settlement
  replay keeps the old row, since it replays the day it describes. The crew prices a run's worst case at
  the output price (the comment in `manifests/49-costcrew.yaml`), so the same ceiling admits more
  Anthropic work and the same tokens cost less. That consequence is derived from the rates and was not run.
- **No flag added or removed** on the console or on `costcrew-run`. The `-due`, `-live` and `-ceiling`
  arguments of the CronJob are unchanged.
- The Go toolchain moved to go1.27.2, and the estate secret scan runs on every pull request and push to
  main. Both are internal to costcrew and change nothing in this launcher.
