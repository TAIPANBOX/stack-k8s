# stack-k8s 1.1.8

One verify check and one stated decision, no image moves. The pinned set is
exactly 1.1.7's.

## What changed

- `verify.sh` asks wardryx's `GET /readyz` (wardryx 1.0.3) beside the five
  `/healthz` probes. A policy plane that cannot reach its store answers 503
  there while `/healthz` stays 200 and every policy write fails; verify now
  reports it (#92).
- The wardryx `readinessProbe` stays on `/healthz`, on purpose, and the
  manifest says why. `POST /v1/decide` does not use the store and keeps
  answering from the policy set in memory. A probe on `/readyz` would take
  the pod out of the Service for the length of a store outage, and every
  gateway with `failmode=closed` would then refuse every call (#92).

## Upgrade

`kubectl apply -k manifests`: the only manifest change is a comment, so no
pod restarts. Run `verify.sh` afterwards to get the new line.

## Not in this release, said plainly

- `verify.sh` with the new line was not run on a cluster. The 1.1.7 tag's
  `verify.sh` ran on a local one-node kind cluster on 2026-09-23 (20 passed,
  0 failed, wardryx `/readyz` store ok), with a hostPath volume standing in
  for the RWX class and Calico, Longhorn and the k3s install path not used.
- On that run wardryx and idryx (uid 65532) could not write the shared
  events volume until it was made writable by hand. The manifests set no
  `fsGroup` for them and rely on the RWX backend exporting a writable
  volume; that dependency is not yet written down anywhere else.
