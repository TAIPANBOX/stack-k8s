# stack-k8s 1.1.49

This release moves the image pins to the 2026-10-17 agent-security wave, and closes the compatibility conflicts
that wave's check found for this launcher. It changes manifests, scripts and documentation. It tags nothing: the
tag is a separate step, taken after the pull request is merged.

## Upgrade

Read this before you apply the manifests to a running cluster. Items 1 and 2 change what a running stack does.
Items 3 to 6 change what you set or expect.

1. **The agent-token audience moved, if the agent-token door is on.** The gateway door, the MCP broker door and
   vouchryx now name one audience, `https://vouchryx.agent-stack.invalid`. They named `http://vouchryx:4310`
   before. tokenfuse v1.17.0 and later refuse a broker whose agent audience is not an absolute https URL, so the
   broker would not start on that tokenfuse with the old value. Run `kubectl apply -k manifests/`, then run
   `./agent-tokens/up.sh` again: the door patches are not in the default apply, so only that script moves them.
   An agent that requests an agent token must ask for the new audience. The workload audience, the one a pod's
   projected service-account token carries, did not change, and stays `http://vouchryx:4310`.
2. **heraldyx 0.8.0 refuses a mail server that does not offer STARTTLS.** The default is `starttls`. A server on
   port 465 needs `HERALDYX_SMTP_TLS=implicit`, and `plain` is allowed only for a loopback relay. Set the variable
   in your environment and run your deploy script again (`deploy.sh`, `cloud/aws/deploy-aws.sh` or
   `cloud/gcp/deploy-gcp.sh`); the script checks the word and writes it into the `heraldyx-mail` Secret. Without
   the key the notifier stays on `starttls`. The dispatch journal, `sent.ndjson`, is created by an init container
   when it is absent; an existing journal is opened as it is.
3. **Stream files: new ones are 0640 and created by their writer.** agent-stack-go v2 creates a missing stream at
   mode 0640, and only in a directory its own uid owns. Each writer's pod now creates its file first, as its own
   uid (`precreate-streams`), and heraldyx does the same for its journal. An existing file keeps its mode and owner
   and is opened as it is. The readers in group 10001 (idryx, the identity sweep and heraldyx) read the bus as before.
4. **The delegation plane's trusted issuers are yours, and change nothing here.** vouchryx 0.5.0 and later refuse a
   subject token that carries no `cnf.jkt`, unless its issuer line ends in `|unbound`. The line in the
   `vouchryx-trusted-issuers` ConfigMap is the one you gave `delegation/up.sh`, and this release does not rewrite it.
   If that line came from the demo IdP (`vouchryx-demo keygen`), it must end in `|unbound`. Never add `|unbound`
   to `VOUCHRYX_WORKLOAD_ISSUERS`: vouchryx refuses to start with it there.
5. **The Keyryx overlay sets a deadline for v2 approval tokens.** With the Keyryx signer on, wardryx 2.2.x verifies a
   v2 HMAC approval token only until `WARDRYX_APPROVAL_V2_UNTIL`. `keyryx/up.sh` sets that to one hour after its
   first run, and keeps an existing value on a re-run, so a re-run does not extend the window. Holds granted before
   the switch return to a person after the deadline.
6. **The images are digest-pinned as before, and their signatures are in the legacy `.sig` format.** Each
   TAIPANBOX image this repository names has a legacy `.sig` tag, probed on the registry on 2026-10-19 (see
   `policy/README.md`). Nothing to do. The admission policy stays opt-in, and whether it admits these digests is not
   measured yet.
7. **tokenfuse stays at v1.16.0 in this release.** The v1.18.0 tag exists, but its images were not on the registry
   when this release was prepared. The door changes above are already in place for v1.17.0 and v1.18.0, so the
   tokenfuse pin is a follow-up change of two image lines and their digests.

## What does not apply, and why

- **XAA on the agent door.** No launcher turns it on, so tokenfuse v1.17.0's rule that XAA and the agent door name
  the same resource does not arise.
- **`VOUCHRYX_SIGNER=keyryx` and `VOUCHRYX_KEYRYX_ROOT_PIN`.** No launcher sets `VOUCHRYX_SIGNER`, so vouchryx 0.6.0's
  root-pin requirement does not arise.
- **CostCrew analyst ids.** This repository has pinned costcrew 0.8.0 since before the wave, and its identity map binds
  `agent://<trust domain>/costcrew/*`. The id change that matters for stack-single is already in place here.
- **Stream writers the table lacked.** heraldyx writes its own journal and is now in the table. `qryx` writes a
  stream only with `--events`, which the crypto-trend job does not pass. `idryx` writes a stream only when
  `IDRYX_EVENTS` is set, which no manifest sets, and its bus mounts are read-only; `identity-sweep` is the same
  shape. Neither needed a writer entry.
- **`stack-caddy` and `stack-wg` at v1.1.48.** No manifest names them. The tunnel builds them locally (`tunnel/`),
  and `tunnel-images.yml` publishes the released ones. Nothing in this repository pins them.
- **trailryx 1.3.x and agent-conform's schema v1.0.** The record seal reads every `*.ndjson` on the bus, including
  `agent-conform.ndjson`, and trailryx 1.3.x counts that schema as unknown. The wave's check does not count this as a
  blocker. It was not re-measured for this release.

## Not measured

- tokenfuse v1.18.0 is not pinned here (see Upgrade, item 7).
- No cluster run of this release. The gates in `CLAUDE.md` run locally; the teeth run is in the pull request.
- The heraldyx journal's fresh-volume start, and the agent-token door on the new broker, need a live run.
  `evidence/agent-tokens-kind/` was measured on the old audience and the old images.
