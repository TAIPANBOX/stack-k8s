# stack-k8s 1.0.0

Deployment three of three of the TAIPANBOX stack: kustomize manifests, the
images this repository composes, and the bring-up for Hetzner, AWS and GCP.
A stack release is a pinned set with a date, nothing more: this one pins the
planes released at 1.0.0 on 2026-09-13 and names the ones that are not there
yet.

## Proven, by the 1.0 proving run (estate-gates `PROVEN.md`, "The 1.0 proving run")

- **INS-5 on this set, R2 GCP, 2026-09-13.** One five-node cluster
  (`c2d-highcpu-8`, k3s + Calico + Longhorn) from bare machines by
  `cloud/gcp`: `terraform apply` 63 s, `deploy-gcp.sh` **12 min 17 s** to
  **verify 15/0/1** and **security-tests 27/0/3**, every image pulled, nothing
  built; the running pods and CronJobs read back with exactly the images
  above.
- **REC-1 on this set.** The three 1.0.0 routines fired by hand from their
  CronJobs, each complete within 15 s: `identity-sweep` raised three alerts on
  the security-tests' probe identity; `record-seal` sealed the tests' ten
  records under `taipanbox.dev` into one segment, proof Full, pack
  **VERIFIED**; `crypto-trend` scanned and said what it could not examine.
- **FAIL-4 on this set.** A freeze written through the admin API into the
  Postgres store: deny before, the policy plane restarted by
  `verify.sh --freeze`, `the freeze survived a policy-plane restart`,
  **16/0/1**, deny after.
- **R2 on the 0.x pins, the same afternoon, GCP and AWS.** Three deploys on
  one GCP cluster (the first red: the installers' missing `gateway_admin`,
  fixed in #73 and gated since), two AWS clusters (the k3s token trap, fixed
  in #74 and gated since), RUN-1 through the real Anthropic API to the 402,
  RUN-8 at 21 000 to 43 000 decisions per second, POL-1, POL-2, POL-4, REC-1,
  REC-2 (a pack verified offline and refused when one byte flipped), INT-4
  (the Terraform provider from the Registry), FAIL-1, FAIL-3, FAIL-4, INS-6
  (the placeholder trust domain, now refused by `verify.sh`).

## Upgrade note, a running cluster to 1.0.0

`kubectl apply -k manifests/` (or the cloud `deploy-*.sh` again, they are
idempotent) rolls the Deployments whose image moved and leaves `policy-db`,
the claims and the Secret alone; the wardryx and idryx schemas migrate
themselves on connect (UPG-2: a wardryx 0.1.0 store on Postgres restored its
policy and its pending holds under 1.0.0). Wardryx approval tokens are
single-use by default from 1.0.0 (`WARDRYX_APPROVAL_SINGLE_USE=false` in the
plane's environment restores the 0.1.0 reuse). Set `--trust-domain` on every
deploy: `verify.sh` fails on the placeholder now.

## Not in this release, said plainly

- The money plane is 0.5.1; its 1.0 follows in the next wave with a minor
  here.
- This tag publishes `genaryx-console`, `stack-caddy` and `stack-wg` at
  `v1.0.0` (the console composition of the five repositories' main branches
  on the day); the manifests keep pinning `v0.1.2` of all three until a run
  proves the new images, the same rule as for every other pin.
- `scopyx` on Kubernetes was not applied in the 1.0-set run (opt-in 47/48);
  the same image was proven on the single-box launcher the same evening.
- Hetzner was not re-run for 1.0 (the 2026-07-25 baseline stands); AWS was
  run on the 0.x pins only.
- `preflight.sh` rewrites `terraform.tfvars` to its default machine type when
  it runs; check the file before `apply` (finding of the 1.0-set run, not
  fixed in this release).
