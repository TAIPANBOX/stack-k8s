# stack-k8s 1.1.10

TokenFuse moves to 1.1.1, and the gateway's semantic cache is switched off
explicitly. Together they remove the gateway's throughput ceiling.

## What changed

- **`tokenfuse` and `tokenfuse-control-plane` are pinned at v1.1.1** (they
  were v1.0.4), for the gateway, its `focus-export` sidecar and the control
  plane. TokenFuse 1.1.0 lies between; its additions are off unless
  configured, so a deployment that sets none of them behaves as before.
- **`TOKENFUSE_CACHE=off` on the gateway container (#96).** With the variable
  unset, TokenFuse up to 1.1.0 ran its semantic cache in shadow mode, which
  compared every call against everything it had stored under one lock, so
  the gateway used about one core, slowed the longer it ran, and at 50 agents
  and more let the policy check time out and refuse legitimate calls. A
  gate, `scripts/gateway-cache-is-off.sh`, fails if the gateway loses the
  setting.

## Measured

Not on a cluster. On one 4-core Intel N150 box running the single-machine
launcher, 100 concurrent agents against a mock upstream: 119 calls/s with
46% refused on TokenFuse 1.0.4, 1987 calls/s with none refused on 1.1.1's
gateway code with the cache off. The published 1.1.1 image with a real
provider (Claude Haiku 4.5, a different prompt on every call) answered all
3,331 calls at 20 and 50 agents with 200.

## Upgrade

`kubectl apply -k manifests`. The gateway and control-plane pods restart
once on the new images.

## Not in this release, said plainly

- The stack was not applied to a cluster with this pinned set. The
  measurements above come from the single-machine launcher on one box.
- An operator who sets `TOKENFUSE_CACHE=shadow` pays for it under varied
  traffic: a new prompt is still compared against every stored entry
  (TAIPANBOX/tokenfuse#329).
