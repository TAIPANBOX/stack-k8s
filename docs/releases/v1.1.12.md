# stack-k8s 1.1.12

The policy store now fails over when the node it runs on dies. Until this
release it waited for that node to come back.

## What changed

- **Longhorn releases a dead node's volumes (#105).** The three installers
  (`install.sh`, `cloud/gcp/install-gcp.sh`, `cloud/aws/install-aws.sh`) set
  Longhorn's `node-down-pod-deletion-policy` to
  `delete-both-statefulset-and-deployment-pod` once Longhorn is ready, and
  stop if they cannot. Longhorn's own default leaves a pod on a dead node
  holding its volume, so a StatefulSet or a Recreate Deployment never starts
  its replacement.
- **The planes with a ReadWriteOnce volume leave a dead node in 30 s (#105).**
  `policy-db`, `tokenfuse-cloud` and the console get the same tolerations
  1.1.11 gave the gateway, wardryx and idryx. A new gate,
  `scripts/longhorn-releases-a-dead-node.sh` (invariant 22), fails if an
  installer loses the setting; invariant 21 now covers every Deployment and
  StatefulSet.

## Measured

On GCP, one cluster of six VMs of three processor families (AMD, Intel and
Ampere arm64) in three zones, with the VM running `policy-db` stopped:

| | policy store unreachable |
|---|---|
| 1.1.11 | until the VM came back |
| 1.1.12, deployed by `deploy-gcp.sh` | about 166 s, then running on another node |

That VM also held one of the three etcd members; the cluster kept its API
throughout. verify.sh 16 passed, 0 failed, and security-tests.sh 27 passed,
0 failed, before and after. While the store is away, wardryx keeps deciding;
what waits is what the store holds, approvals and freezes.

The same cluster also ran 1.1.10 and upgraded to 1.1.11 live, with every
plane moved onto the arm64 nodes and back.

## Upgrade

`kubectl apply -k manifests` restarts `policy-db`, `tokenfuse-cloud` and the
console once. An existing cluster also needs the Longhorn setting, which only
the installers write:

    kubectl -n longhorn-system patch settings.longhorn.io node-down-pod-deletion-policy \
      --type merge -p '{"value":"delete-both-statefulset-and-deployment-pod"}'

## Not in this release, said plainly

- `install.sh` (Hetzner) and `install-aws.sh` were not run with the new
  block; it is the same block the GCP installer ran, through an identical
  helper on AWS.
- Only `policy-db`'s node was stopped. `tokenfuse-cloud` and the console fail
  over by the same mechanism, not measured.
- A network partition, as opposed to a stopped VM, was not tested.
- `security-tests.sh` does not parse under macOS `/bin/bash` 3.2 (#104); the
  deploy scripts run it on a node, where it passes.
