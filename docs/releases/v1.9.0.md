# stack-k8s 1.9.0

A minor release. The fire drills reach the MCP broker with a key of their own and run as a job beside it, every static key the broker admits is now a gateway key of the same id, which also mends the typed door's own caller key, and tokenfuse moves to v1.24.0 and mockryx to v0.5.0.

## Upgrade first

1. **A cluster whose gateway client keys are your own (`identity/up.sh` with a keys file) needs two more keys before you deploy.** The gateway's static-key list now names `drills-broker` and `broker-caller`, and a gateway whose list names a key it does not hold refuses to start. The launchers check this before they apply anything and stop with this item's name, so nothing goes down; a cluster whose keys a deploy minted needs nothing, the deploy adds both. From the directory that holds your two files (`keys.txt` and `identity.json` here), with `kubectl` on the cluster:

   ```bash
   # drills-broker: a new secret, also given to the broker drills' job as drills-broker-key.
   DB="$(head -c 4096 /dev/urandom | LC_ALL=C tr -dc 'A-Za-z0-9' | cut -c1-40)"
   printf '%s:drills-broker\n' "$DB" >>keys.txt
   printf '%s' "$DB" | kubectl -n agent-stack create secret generic drills-broker-key --from-file=broker_key=/dev/stdin
   # broker-caller: the secret your typed door already holds, or a new one when it has none.
   BC="$(kubectl -n agent-stack get secret tokenfuse-mcp-broker-keys --ignore-not-found -o jsonpath='{.data.TOKENFUSE_MCP_KEYS}' \
     | base64 -d | tr ',' '\n' | sed -n 's/:broker-caller$//p' | head -n 1)"
   [ -n "$BC" ] || BC="$(head -c 4096 /dev/urandom | LC_ALL=C tr -dc 'A-Za-z0-9' | cut -c1-40)"
   printf '%s:broker-caller\n' "$BC" >>keys.txt
   unset DB BC
   ```

   Then bind both in `identity.json`'s `keys[]`, each in a unit the map declares (these are the units a minted map uses):

   ```json
   {"key_id": "drills-broker", "unit": "drills", "agents": ["agent://mockryx.local/*"]},
   {"key_id": "broker-caller", "unit": "broker", "agents": ["agent://<your trust domain>/typed-broker"]}
   ```

   and hand both files over, then deploy:

   ```bash
   ./identity/up.sh --client-keys-file keys.txt --identity-map-file identity.json
   ```

2. **Re-run the launcher, or apply the manifests of this tag.** Images move by tag and digest:

   | Image | 1.8.9 | 1.9.0 |
   |---|---|---|
   | tokenfuse (gateway, MCP broker, `focus-export`, the console's tokenfuse engine) | v1.23.0 | v1.24.0 |
   | tokenfuse-control-plane | v1.23.0 | v1.24.0 |
   | mockryx (`drills`, and the new `drills-broker`) | v0.4.0 | v0.5.0 |

   The pinned console image keeps the tokenfuse engine it was built with until the next console tag; `images/console.Dockerfile` names v1.24.0 for that build.

3. **A cluster whose keys a deploy minted gets the two keys on the deploy.** The deploy keeps the five it has byte for byte and adds `drills-broker` and `broker-caller`, taking `broker-caller` from the typed door's own Secret when the cluster has one, so an agent that holds it keeps working. The gateway rolls once more than usual on this deploy: the new list reaches it with the apply, and the keys right after.

4. **The typed door's static callers now pass the gateway's tool-call check.** Since 1.5.0 the broker asked that check about every tool call with the caller's own key, the gateway did not hold `broker-caller`, and every call with it was refused `-32004 blocked: the taint gate answered 401` (or, with no `x-fuse-run-id`, `the taint gate needs x-fuse-run-id`). A call with it now reaches wardryx, which holds it for a person until a grant names the tool (the tool hold, invariant 83). A call must still name its run in `x-fuse-run-id`.

5. **The broker drills are a job of their own.** `drills-broker` ships suspended beside the broker (`manifests/52-tokenfuse-mcp-broker.yaml`, so only with the typed-answer door). Run it with `kubectl -n agent-stack create job --from=cronjob/drills-broker drills-broker-now`. All three pass on a cluster with no MCP server: the secret drill, the PII drill as `skipped_not_configured` (PII runs in shadow), and the cluster's own tool-hold drill, `mcp-ungranted-tool-held-on-this-cluster` from the ConfigMap `drills-broker-scenarios`, mounted over the image's. Its first call is held for a person, which opens one pending approval on wardryx that later runs reuse, and its second, as a drill identity, is refused by the broker's vault (`-32008`) because the `{{secret:typryx_key}}` handle is scoped to typryx's own tools. mockryx's own version asks for a result from an MCP server that answers `search_notes`, which this stack does not run.

## What changed

- **The drills' broker key** (CLAUDE.md invariant 85). `lib/identity-mint.sh` mints `drills-broker` into `gateway-client-keys` and the Secret `drills-broker-key`; `typed/mode.sh` gives the broker the same entry; the `drills-broker` CronJob sends it as `x-fuse-key` to the broker alone, from a 0440 file. Two NetworkPolicies open that pod to the broker on 4200 and nothing else.
- **`broker-caller` is a gateway key** of the same id and secret, bound to exactly `agent://<trust domain>/typed-broker`. `typed/mode.sh door-callers` keeps a broker Secret made before this release in step: an entry it lacks is appended, every entry it had stays byte for byte, and one whose secret is not the gateway's stops the deploy with what to do.
- **`identity_mint_guard`** runs before the first apply in all three launchers.
- **tokenfuse v1.24.0**: under `TOKENFUSE_WARDRYX_MODE=enforce` the broker's `tools/list` leaves out the tools wardryx refuses the named agent outright (`deny_tool`, or outside an `allow_tool` list).
- **mockryx v0.5.0**: a key of the broker's own (`--mcp-broker-key-file`, `$MOCKRYX_MCP_BROKER_KEY_FILE`), refused when it is the gateway client key, and the tool-hold drill.
